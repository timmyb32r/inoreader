# Inoreader: спецификация первой версии

Дата: 25 сентября 2026. Рабочее имя проекта: `inoreader`.

Статус: deep-interview завершён; продуктовые решения первой версии согласованы, известных существенных открытых продуктовых вопросов не осталось. Полноценный поиск отложен, в v1 предусмотрена только заглушка. Технические гипотезы и подготовка окружения перечислены в §15.2 и требуют проверки перед соответствующими этапами. Это спецификация для последующей реализации; наличие документа не означает, что приложение, импорт или инфраструктура уже работают.

## 1. Цель и статус решений

Создать личную многопользовательскую RSS-читалку с привычными сценариями Inoreader, автоматическим получением полного текста, конструктором лент для сайтов без RSS и бессрочным архивом. Сразу включить возможности существующего `personal_feed` в общую инфраструктуру нового проекта. Сначала сделать описанную здесь первую версию; собственные дополнительные функции развивать после неё.

В документе используются три статуса:

- **Согласовано** — прямые решения пользователя в интервью и решения по явно делегированному им выбору, обязательные ограничения. Делегированные решения отмечаются отдельно.
- **Предлагаемый контракт** — конкретные детали, которыми эта спецификация закрывает оставшиеся неоднозначности. Они вынесены на ревью вместе с документом, а не выдаются за отдельные ответы пользователя.
- **Требует проверки** — факт о внешней системе или техническая гипотеза, которую необходимо проверить до соответствующей реализации.

Если ниже не указан отдельный статус, детали поведения являются предлагаемым контрактом первой версии. Изменение согласованных ограничений требует отдельного решения.

### 1.2. Границы первой версии

Включены чтение RSS/Atom/JSON Feed, подписки, пространства, просмотр всех/непрочитанных, избранное, «прочитать позже», заглушка поиска, OPML import/export, простые правила, корзина, автоматический полный текст, Web feeds и импорт начальных источников.

**Согласовано:** избранное (`saved`) и «позже» (`later`) — независимые булевы состояния, не система тегов. Изменение одного не меняет другое или read/unread; явное открытие статьи не снимает эти отметки.

**Согласовано:** интерфейс первой версии только на английском; переключение языка и дополнительные локализации не входят в v1. Русские названия действий в этой спецификации описывают их смысл, а не буквальный текст будущих UI-кнопок.

Не включены полноценный поиск и поисковая индексация, перевод, AI-функции, папки, теги, публичная регистрация, совместные пространства, биллинг, собственные мобильные приложения, newsletter-to-email, самостоятельные Telegram/социальные коннекторы, история редакций статей, Track changes для произвольных изменений страницы, сайты с авторизацией, обход CAPTCHA/paywall, произвольные пользовательские скрипты, экспорт публичных RSS для третьих лиц и миграция истории прочтений из Inoreader. Обычная публичная RSS-ссылка Telegram/YouTube/другого сервиса обрабатывается как лента, если она доступна без специальных интеграций.

**Согласовано:** в v1 входит дедупликация по точному совпадению тройки URL + заголовок + описание, включая поступления из разных лент в одном пространстве. Если URL совпал, но заголовок или описание отличаются, это отдельные статьи. Поиск дублей по похожему тексту, похожим заголовкам, очищенным URL и другие расширенные способы пользователь и разработчик спроектируют отдельно позднее. Идемпотентная обработка повторного получения той же записи из той же ленты также обязательна.

Бессрочное хранение не означает автоматическую загрузку всей исторической глубины сайта, которая не представлена в доступной ленте или выбранных страницах. Первая загрузка и глубина обхода задаются явно; найденные статьи не вытесняются новыми поступлениями. Замена редакции той же статьи разрешена согласованной политикой последней успешной редакции.

## 2. Аккаунты и пространства

Аккаунт — граница владения и авторизации. Пространство — самостоятельная библиотека внутри аккаунта. Общего списка непрочитанных сразу по всем пространствам в первой версии нет: активное пространство видно в интерфейсе и во всех относящихся к нему URL.

Каждому пространству принадлежат подписки, их пользовательские названия и настройки, правила, библиотека статей, read/unread, избранное, «позже» и корзина. Создание, переименование и переключение доступны в интерфейсе. Имена на русском и английском сохраняются в введённом виде; внутренний ID не зависит от имени. Переименование не меняет идентичность и данные пространства.

Один публичный источник можно добавить в несколько пространств и аккаунтов. Его получение и неизменяемый контент допустимо разделять внутри backend. Подписки и пользовательское состояние всегда отдельные. Наличие общего контента не предоставляет доступ к чужим библиотекам, рецептам Web feeds, правилам, статистике или списку подписчиков.

**Согласовано:** закрытая регистрация по одноразовым приглашениям администратора; сброс пароля через администратора, без самостоятельного восстановления по email в v1. Первый администратор создаётся отдельной командой с интерактивным вводом пароля, без пароля в аргументах процесса или примерах конфигурации. Приглашение ограничено сроком, одноразовое потребление атомарно; повторная активация не создаёт второй аккаунт. Администратор выпускает одноразовую ссылку сброса. Администратор не получает отдельный интерфейс чтения библиотек друзей.

Пароли хешируются предназначенным для паролей алгоритмом, предлагается Argon2id с проверенными на целевом сервере параметрами. Сессии — случайные непрозрачные токены; на сервере хранится их безопасное проверочное представление. Cookie `HttpOnly`, `Secure` для внешнего HTTPS, `SameSite`; защита изменяющих запросов от CSRF, ограничение попыток входа и отзыв сессий при смене пароля. Вход, выход, смена пароля и управление приглашениями входят в первую версию.

Backend получает пользователя из сессии, проверяет владение пространством и создаёт валидированный `NamespaceScope`. Переданный клиентом `user_id` не считается доказательством прав. Эта проверка обязательна также для фоновых задач, экспорта, массовых действий, просмотра полного текста и сессий конструктора. Угаданный чужой ID не раскрывает существование или содержимое объекта.

## 3. Основные сценарии читалки

### 3.1. Экран чтения

**Согласовано:** навигация, кнопки, настройки, формы авторизации, подсказки, справка по горячим клавишам, доступные подписи и пользовательские сообщения об ошибках — на английском. Locale браузера не переключает язык приложения. Исходные тексты и метаданные статей, названия источников, пространств, подписок и правил сохраняются в введённом или полученном виде, включая русский и китайский; английский UI не ограничивает языки содержимого.

Предлагаемая компоновка: выбор пространства и подписки слева, список статей в центре, чтение выбранной статьи в отдельной панели или полноширинном режиме. На узком экране эти области переключаются последовательно. Представления: все статьи, непрочитанные, избранное, позже, корзина и выбранная подписка.

Строка статьи показывает источник или несколько источников статьи, объединённой по URL, заголовку и описанию, её заголовок, дату, состояния и короткий фрагмент, если он есть. Просмотр статьи содержит доступный текст, автора и дату при наличии, ссылку на оригинал, связи с подписками и состояние получения полного текста. Язык исходной статьи не меняется.

**Согласовано:** статья отмечается прочитанной при явном открытии пользователем; предзагрузка и попадание строки в viewport не меняют состояние. Есть явные read/unread, избранное, позже, корзина и восстановление. Изменения подтверждаются в месте действия сразу; при ошибке сохранения интерфейс показывает ошибку и возвращает согласованное состояние. Незавершённая операция не выглядит успешно сохранённой.

Сортировка по умолчанию — новые поступления первыми, с выбором обратного порядка. Курсорная пагинация использует стабильную пару времени поступления в библиотеку и ID, а не смещающийся `OFFSET`. Новые поступления предлагаются отдельным счётчиком и не сдвигают список под указателем или во время чтения. Переключение пространства восстанавливает его собственную позицию чтения.

«Отметить всё прочитанным» фиксирует область действия и верхнюю границу уже существовавших поступлений. Статьи, добавленные после этой границы, остаются непрочитанными. Массовая операция возобновляется после прерывания и показывает прогресс. Конкурирующие ручные изменения не затираются слепым повтором устаревшей операции.

Клавиатура: следующая/предыдущая статья, read/unread, избранное, позже, оригинал, закрыть панель. Горячая клавиша поиска в v1 не назначается; состояние заглушки описано в §10.2. Конкретная раскладка уточняется при сверке с Inoreader; справка доступна в UI. Горячие клавиши не перехватываются при наборе в полях. Доступны управление фокусом, видимые состояния фокуса, подписи элементов и светлая/тёмная тема.

**Согласовано:** сохранить знакомые сценарии Inoreader и сделать собственный интерфейс проекта. Компоновка, компоненты и визуальные детали проектируются для этой читалки с опорой на semantic tokens, cool slate + teal, светлую/тёмную тему и правила стабильного layout. Пиксельное совпадение с Inoreader не является целью или критерием приёмки. Для Web feeds сохраняется согласованный сценарий визуального выбора элементов, оформленный в том же собственном UI. Финальная компоновка основного экрана проходит отдельное визуальное ревью по этому направлению.

### 3.2. Подписки и импорт

Добавление принимает URL ленты или публичной страницы. Для страницы сначала ищутся объявленные RSS/Atom/JSON Feed; если вариантов несколько, пользователь выбирает. При отсутствии ленты можно перейти к Web feed. После проверки показываются название, тип, URL, несколько статей и целевое пространство; создание происходит после выбора пользователя.

Подписка поддерживает пользовательское название, ручное обновление, паузу, просмотр ошибок и времени последнего успешного обновления, настройку правила и отписку. Повторное добавление того же источника в то же пространство явно предлагает уже существующую подписку; добавление в другое пространство создаёт независимую подписку.

**Согласовано:** пауза останавливает плановые обновления ради этой подписки и доставку через неё новых статей и исходных редакций. Если тот же источник нужен другим активным подпискам, его общий сбор продолжается. Если активных подписок больше нет, новые плановые опросы не запускаются. Уже полученные статьи и задания извлечения их полного текста не удаляются; извлечение завершается по обычным правилам retry. Приостановка одной подписки не останавливает доставку через другие активные подписки того же пространства, в том числе для статьи, объединённой по ключу дедупликации.

Пауза фиксирует границу доставки. Выполняющееся получение может сохранить исходный результат, но перед публикацией в библиотеку fan-out повторно проверяет состояние и версию подписки: после фиксации паузы он не продолжает её доставку по устаревшему состоянию. Прогресс и полученные данные сохраняются для возобновления. Уже доставленные статьи завершают обработку по неизменённым включённым правилам согласно §4; сама пауза не отменяет ожидающие действия этих правил.

**Согласовано:** каждое действие `Pause subscription` требует заполнить `Reason`. Отсутствие поля, пустая строка и строка только из пробельных символов отклоняются до изменения состояния подписки. Пользовательский текст сохраняется в введённом виде: проверка непустоты не обрезает, не переводит и не заменяет его шаблонной причиной. Максимальный размер в UTF-8 байтах задаётся явным `subscriptions.pause_reason_max_bytes`, валидируется при запуске и одинаково проверяется frontend/backend; превышение возвращает ошибку без усечения. Простой неуспех опроса остаётся диагностируемой ошибкой источника и не создаёт неявную пользовательскую паузу.

Причина, время и инициатор сохраняются атомарно с переходом в paused и доступны владельцу рядом со статусом подписки. После возобновления запись о причине остаётся в истории подписки; новая пауза требует новой причины и не перезаписывает предыдущую. Валидированное состояние `Paused` невозможно создать или восстановить из хранилища без валидной причины. UI запрашивает её в стабильном диалоге с общим autofill-resistant полем; на подтверждении сразу показывает pending и предотвращает повторную отправку, при ошибке сохраняет введённый текст. Backend применяет те же ограничения для прямого API-вызова; повтор одного запроса не создаёт дублирующие переходы или записи истории.

**Согласовано:** после возобновления подписка продолжает с сохранённой границы доставки и догружает пропущенное, которое уже сохранено общим сборщиком либо ещё доступно в ленте/листинге. Загрузка идемпотентна, возобновляется после сбоя и не сбрасывает состояния ранее доставленных статей. Уже исчезнувшие из источника и никогда не полученные записи гарантированно восстановить нельзя; UI явно сообщает об этом ограничении. Возобновление не подключает незаметно всю историю общего источника до первоначально выбранной области подписки.

Отписка прекращает будущую доставку, но сохраняет библиотеку, текст и состояния ранее полученных статей. Архивные подписки остаются доступны через настройки/фильтр архива. Повторная подписка предлагает восстановить прежнюю связь. Удаление пространства в v1 заменяется явно названной операцией «Архивировать пространство» с возможностью восстановления. Безвозвратного удаления статей, очистки корзины по таймеру и автоматического удаления аккаунтных библиотек нет.

**Согласовано:** `Archive workspace` запрашивает одну общую обязательную `Reason` и приостанавливает обновления и доставку для всех подписок пространства. Причина проходит ту же централизованную проверку непустоты и UTF-8 размера, что и причина индивидуальной паузы; используется общий предел `subscriptions.pause_reason_max_bytes`. Введённый текст, автор и время сохраняются атомарно с архивированием. Операция не удаляет библиотеку, состояния и связи с источниками; сохранённые статьи остаются доступны для чтения, уже начатое получение их полного текста завершается как при паузе подписки.

Индивидуальные состояния подписок не перезаписываются общей паузой. Архивирование пространства — отдельное основание остановки: для ранее активной подписки UI показывает общую причину со ссылкой на событие архивирования; у уже приостановленной подписки сохраняются её собственная причина и история. Архивные подписки также не активируются. Пока пространство архивировано, ни пользовательский API, ни scheduler/fan-out не могут возобновить его доставку в обход статуса пространства. Общий источник может продолжать сбор для других активных пространств и аккаунтов; их работа не изменяется.

**Согласовано:** `Restore workspace` снимает только остановку, вызванную архивированием пространства. Автоматически возобновляются лишь подписки, которые были активны перед архивированием; индивидуальные паузы с их причинами и отписки сохраняются. Для возобновлённых подписок выполняется догрузка по согласованному контракту resume. История общей причины остаётся доступной после восстановления. Граница архивирования/восстановления проверяется вместе с версией подписки перед публикацией доставки; retry и авария не могут оставить часть подписок работающей в архивированном пространстве или снять индивидуальную паузу. UI подтверждает переход немедленно через pending и сохраняет стабильность диалога и списка.

OPML импортируется сначала в предпросмотр: количество элементов, дубликаты, неподдерживаемые/повреждённые записи, назначенное пространство. Иерархия папок входного OPML не переносится: интерфейс явно сообщает, что все выбранные подписки попадут непосредственно в выбранное пространство. Частичный импорт допустим только как явный выбор с отчётом по каждой записи. Повторный импорт идемпотентен. OPML-экспорт включает стандартные feed URL; для Web feeds без публичного feed URL отдельно предоставляется экспорт рецептов проекта, без выдуманных RSS-адресов.

### 3.3. Каталог и карточка подписки

#### Цель и навигация

Подписка — самостоятельная пользовательская сущность, а не только фильтр списка
статей. Боковая панель остаётся быстрым путём к потоку статей: нажатие на
подписку открывает её статьи. Заголовок **Subscriptions** ведёт в каталог,
строка каталога — на устойчивый адрес `/subscriptions/:id`, а **View all
articles** в карточке возвращает к потоку этой подписки. Контекстное меню
подписки в боковой панели содержит **View details**, **Refresh** и **Pause**.

Каталог `/subscriptions` использует три представления: **Current** для активных,
приостановленных и ошибочных подписок, **Needs attention** для источников,
требующих действия, и **Archived** для отписок с возможностью восстановления.
Намеренная пауза сама по себе не требует внимания. Причина Needs attention
всегда выводится текстом; статус нельзя передавать только цветом.

#### Каталог

На desktop каталог представлен плотной таблицей. По умолчанию видны **Name**,
**Type**, **Status**, **Last updated** и **Unread**; пользователь может включить
URL, personal note, частоту обновления, актуальную ошибку и дату добавления,
изменить порядок и ширину колонок. Набор колонок, порядок, ширины и сортировка
сохраняются отдельно для каждого workspace. Изменение набора колонок применяется
явно и не сдвигает активные controls во время взаимодействия.

Локальный мгновенный поиск каталога сопоставляет название, URL и personal note и
не зависит от заглушки полнотекстового поиска статей. Фильтры покрывают статус и
тип источника; сортировки — название, время последнего успешного обновления и
число непрочитанных. На узком экране таблица становится вертикальным списком без
горизонтальной прокрутки: название и статус видны всегда, выбранные дополнительные
поля раскрываются внутри строки, а детали открываются отдельным экраном.

Таблица поддерживает выбор нескольких строк и только две массовые операции в
этом объёме: **Refresh** и **Pause**. Массовая пауза требует одну явную причину,
проходит те же проверки, что индивидуальная пауза, и сообщает результат по каждой
выбранной подписке. Массовых Move to workspace и Archive нет.

#### Карточка подписки

Карточка содержит вкладки:

- **Overview**: отображаемое и обнаруженное названия, URL, personal note,
  состояние, статистика и пять последних статей;
- **Extraction**: тип источника, читаемое описание действующего рецепта,
  обнаруженные feed URL и результат последнего preview;
- **Rules**: собственные правила подписки и отдельно правила workspace, которые
  воздействуют на её статьи;
- **Activity**: попытки обновления, длительность, число найденных материалов и
  диагностированные ошибки.

Обнаруженное **Source title** и необязательное **Custom name** хранятся отдельно.
Custom name определяет отображение; его очистка возвращает Source title.
**Personal note** — одно обычное многострочное текстовое поле без Markdown.
Заметка сохраняется только через **Save note**: после изменения виден постоянный
индикатор **Unsaved changes**, а внутренняя навигация, смена workspace, reload и
закрытие вкладки требуют подтверждения. Сохранение немедленно показывает pending,
блокирует повторную отправку и при ошибке сохраняет введённый текст.

URL доступен через **Open**, **Copy** и **Change source URL**, но не редактируется
как обычное поле. Новый URL сначала проходит серверную проверку и preview; до
явного подтверждения действует прежний адрес. Для Extraction изменение рецепта
открывается отдельным действием **Edit extraction recipe** и разрешает сохранение
только после успешного серверного preview. Обычная лента показывает тип и
обнаруженные адреса вместо неприменимых HTML selectors.

Локальные правила редактируются из карточки через обязательный preview. Влияющие
правила workspace показывают действие и ведут в общий раздел **Rules**. Overview
показывает пять последних статей и ссылку **View all articles**, но не дублирует
полный reader.

Подробные Activity events хранятся и показываются 30 дней. Даты последнего успеха
и последней ошибки, а также актуальная ошибка сохраняются бессрочно. Подписка
попадает в Needs attention после трёх последовательных неудачных обновлений,
трёх пропущенных ожидаемых обновлений, при незавершённом импорте/рецепте либо
когда ранее работавший preview рецепта больше не находит статей.

#### Владение, идентичность и границы совместного получения

Подписка и все её данные принадлежат одному пользователю и одному workspace.
Заметки, пользовательские и исходные названия, рецепты, правила, activity,
ошибки, статьи и состояния никогда не видны другому пользователю. Backend выводит
владельца из сессии и проверяет его для каждого списка, lookup, изменения и
экспорта; угаданный ID не раскрывает существование чужой подписки.

Одинаковый публичный URL допускает общий безопасный fetch и общий неизменяемый
сырой результат ниже пользовательской границы. Fan-out создаёт независимые
пользовательские данные. Запросы с credentials, cookies, private headers или
персонализированной конфигурацией не объединяются. Действие одного пользователя
никогда не влияет на другого.

Один пользователь может иметь независимые подписки на одинаковый URL в разных
workspace; их имена, заметки, правила и состояния статей разделены. Внутри одного
workspace точное повторное добавление RSS/Atom/JSON Feed URL открывает имеющуюся
подписку. Одна web page может иметь несколько подписок с разными extraction
recipes. URL сравнивается в сохранённом виде без скрытой нормализации. Перенос
подписки между workspace в этот объём не входит.

#### Не входит в объём и риски

В этот этап не входят Markdown-заметки, совместные заметки, массовое архивирование,
перенос подписок между workspace и полный поток статей внутри карточки. Основные
риски — утечка данных через lookup/list/export, смешивание user state в общем
fetch cache, потеря несохранённой заметки и нестабильная таблица. Их закрывают
server-side ownership predicates, tenant-free cache keys и payloads, явное
сохранение с navigation guard, стабильная геометрия controls и обязательные
cross-user/component/browser regression tests. Неразрешённых продуктовых
вопросов для этого раздела нет.

### 3.4. Корзина

Корзина относится к конкретной статье библиотеки конкретного пространства. Она исключает статью из обычных представлений и счётчика непрочитанных, сохраняя прежний read/unread, избранное и «позже». Восстановление возвращает эти состояния. Полный текст и источник не удаляются. В корзине доступны просмотр списка, чтение и восстановление. Видны причина удаления и сработавшее правило, если действие было автоматическим.

## 4. Правила и фильтры

Первая версия разделяет фильтры просмотра и изменяющие состояние правила. Фильтры просмотра — подписка, read/unread, избранное/позже, диапазон даты и включение корзины. Они ничего не изменяют в библиотеке.

Контракт правила:

- Область проверки — одна подписка в одном пространстве; имя, включено/выключено, список искомых слов или фраз. Область действия при совпадении — общая библиотечная статья этого пространства.
- Поле — заголовок, доступный текст либо оба; начальное значение в форме — заголовок. Пользователь видит и выбирает поле до сохранения.
- **Согласовано:** буквальное вхождение подстроки без учёта регистра; `career` совпадёт и с `careers`. Режим списка — «любое из перечисленных». Без regex, морфологии и неявной транслитерации. Нормализация применяется только к сравнению, оригинал сохраняется.
- Действие — `mark_read` или `move_to_trash`; другие действия и цепочки не включены.
- До сохранения есть предпросмотр совпадений на уже сохранённых статьях с указанием поля, найденного фрагмента и подписки, по данным которой найдено совпадение. Форма и предпросмотр явно сообщают: действие меняет статью во всём текущем пространстве, включая её отображение в других связанных лентах; показаны эти связи и число уникальных затронутых статей.

Правила запускаются при поступлении статьи через соответствующую подписку, включая добавление нового источника к уже существующей библиотечной статье. При доставке атомарно фиксируются применимые включённые правила и их версии. Появление нового полного текста продолжает оценку по тексту только для зафиксированных применимых версий, которые остаются включёнными и неизменёнными; обновление уже доставленной исходной записи или её fulltext само по себе не подключает новые правила к архиву. Правило подписки проверяет заголовок/текст её исходной записи и относящийся к ней полный текст; выбор заголовка общей карточки не подменяет вход правила. Версия правила, подписка, версия входного контента и результат оценки сохраняются; повтор задачи не повторяет логическое действие. Нельзя оценивать неподгруженный текст как достоверное отсутствие совпадения: статус проверки по полному тексту остаётся ожидающим или завершённым с ошибкой извлечения.

Несколько правил вычисляются независимо по зафиксированным версиям соответствующих входных записей. Их действия объединяются детерминированно: совпавшее `mark_read` устанавливает прочитано, `move_to_trash` добавляет корзину; при обоих сохраняются оба состояния. Порядок списка правил на результат не влияет. Отсутствие совпадения после последующего изменения текста не отменяет прежнее действие автоматически.

**Принято по делегированному пользователем выбору:** этот контракт действует и между правилами разных подписок, связанных с одной статьёй по полному ключу дедупликации (URL, заголовок и описание). `move_to_trash` любой из них помещает общую статью в корзину во всём текущем пространстве; `mark_read` отмечает её прочитанной во всех его представлениях. Отсутствие правила или совпадения в другой подписке не отменяет действие. Отдельных состояний скрытия/прочтения для каждой связи с лентой нет. Статьи с одним URL, но разными заголовками или описаниями имеют независимые состояния и правила одной не меняют другую. Диагностика сохраняет все сработавшие правила и их подписки; между пространствами действия не распространяются.

Ручное действие имеет приоритет. «Сделать непрочитанным» защищает read-state этой статьи от последующих автоматических `mark_read`; восстановление защищает её от повторного автоматического помещения в корзину. Защита относится к общей статье в пространстве и действует против правил всех связанных подписок, включая добавленные позднее. Поздняя загрузка полного текста, поступление точного дубля из другой ленты и retry не отменяют эти действия. Повторное применение правил вручную может снять защиту только после явного выбора в предпросмотре. Оценка и изменение состояния проверяют версию записи, чтобы не перезаписать более новое ручное действие.

**Согласовано:** создание/редактирование правила влияет только на новые поступления. Изменение, выключение или удаление правила отменяет все ещё не выполненные действия прежней версии, включая ожидающие fulltext и уже вычисленные, но ещё не записанные результаты. Перед атомарным изменением статьи проверяются существование, включённость и актуальность версии правила вместе с версией состояния статьи и ручными overrides. Проверки только при запуске задачи недостаточно. При конфликте устаревшее действие не публикуется; его отмена с причиной сохраняется в диагностике. Повторное включение создаёт новую версию применимости и не оживляет отменённые задачи. Уже выполненные действия не отменяются автоматически при изменении, выключении или удалении правила; причины этих действий остаются доступными.

Старый архив обрабатывается отдельной явной командой «Применить к существующим» с предпросмотром, границей выборки, зафиксированной версией правила и возобновляемым прогрессом. Изменение, выключение или удаление этой версии отменяет оставшиеся действия массового запуска, сохраняя выполненные и видимую причину остановки; новая версия требует нового явного запуска. Конкуренция редактирования с доставкой/действием разрешается атомарной границей фиксации: действие, записанное до изменения правила, остаётся, а после изменения прежняя версия уже не может менять состояние. Retry/restart сохраняют эту границу и не повторяют действия.

**Согласовано:** пауза подписки или архивирование пространства не отменяет ожидающую обработку уже доставленных статей по неизменённым включённым правилам, в том числе после получения полного текста. Изменение, выключение или удаление самих правил отменяет ожидающие действия и в этих состояниях. Пример изоляции: правило `career → корзина` у подписки в `data-engineering` не меняет ту же статью в `финансы`.

## 5. Получение статей и полного текста

### 5.1. Единый конвейер

Один scheduler обслуживает обычные ленты, Web feeds и перенесённые адаптеры `personal_feed`: планирование → получение → разбор → сохранение → доставка в библиотеки → правила → получение полного текста → повторная оценка правил по тексту. Работа разбивается на устойчивые задания; медленный сайт не держит транзакцию базы и не блокирует чтение.

Для RSS используются условные HTTP-запросы с ETag/Last-Modified, когда их поддерживает источник. `304` не создаёт новых статей. Уважать `Retry-After`, ограничивать параллелизм глобально и на origin, применять ограниченные повторы с задержкой. Лимиты и интервалы задаются конфигом и видны в диагностике. Ошибка одного источника не останавливает остальные.

Идентичность входной записи задаётся документированным контрактом адаптера: стабильный GUID/ID внутри источника, иначе точный абсолютный URL внутри источника. У записи без обоих — явная ошибка идентификации; заголовок и текущая дата не становятся скрытой заменой отсутствующего upstream ID. Идентичность входной записи нужна для ingest и обновлений и отделена от ключа дедупликации статей в библиотеке.

**Согласовано:** поступления из разных RSS-лент объединяются в одну библиотечную статью внутри пространства только при совпадении URL, заголовка и описания. Если отличается хотя бы заголовок или описание, при том же URL создаются разные статьи с независимыми состояниями. У точных дублей ручные состояния прочтения, избранного, «позже» и корзины общие; в другом пространстве состояния остаются независимыми. В общей выдаче и счётчиках объединённая статья учитывается один раз, в фильтре каждой из связанных подписок доступна та же запись. Позднее поступление точного дубля добавляет связь с источником; сама привязка не сбрасывает состояния и время первого поступления в библиотеку. Правила новой подписки отдельно применяются по §4 с сохранением приоритета ручных overrides.

Контракт сравнения в v1 — точное совпадение абсолютного URL статьи после разрешения относительной ссылки и исходных значений заголовка и описания, полученных parser. Описание — поле description/summary исходной записи по документированному контракту адаптера, а не заново сгенерированный excerpt или автоматически извлечённый полный текст. Исходное представление URL также сохраняется. Query-параметры, fragment, порядок параметров, завершающий слеш и различие HTTP/HTTPS не удаляются и не переписываются ради объединения; конечный адрес redirect и HTML canonical не подменяют ключ. Регистр, пробелы и HTML в заголовке/описании не нормализуются ради дедупликации; сравнение предшествует преобразованию для безопасного отображения. Отсутствие поля отличается от пустой строки. Одинаковые GUID или текст из разных источников при разных URL не объединяют статьи. Запись без URL, но со стабильным ID остаётся отдельной по паре источник + ID; совпадение отсутствующих URL не является основанием для объединения.

Объединение сохраняет происхождение и последние успешные данные каждой входной записи. При разных заголовках или описаниях одного URL выбирать «основную» ленту не требуется: каждая отдельная статья показывает свои данные; они не объявляются редакциями друг друга и не затираются случайным last-write-wins. Последующие изменения URL, заголовка или описания могут изменить совпадение уже доставленных записей.

**Согласовано:** при разделении объединённой статьи после изменения заголовка/описания одного источника обе получившиеся статьи наследуют её текущее состояние прочтения. Если общая статья уже прочитана, обе остаются прочитанными; обновление само по себе не создаёт непрочитанное поступление. Разделение не затирает более новое ручное действие устаревшим снимком состояния; retry не создаёт повторных библиотечных записей.

**Согласовано:** если уже существующие отдельные библиотечные статьи после обновления совпали по URL, заголовку и описанию и объединяются, результат непрочитан при наличии хотя бы одной непрочитанной статьи. Результат прочитан только тогда, когда прочитаны все объединяемые статьи. Решение использует актуальные состояния в момент атомарного объединения и не затирает более новое ручное действие. Это правило относится к объединению существующих библиотечных записей: поступление нового точного дубля из другой ленты без отдельной библиотечной записи лишь добавляет связь и не сбрасывает прочитанность уже существующей статьи.

**Согласовано:** при разделении каждая получившаяся статья наследует избранное (`saved`), «позже» (`later`), корзину (`trash`), ручную защиту от автоматических правил и время первого поступления исходной общей статьи. После разделения эти состояния независимы. При объединении уже существующих статей:

- `saved` и `later` сохраняются независимо друг от друга, если соответствующая отметка есть хотя бы у одной статьи.
- `trash` сохраняется только тогда, когда все объединяемые статьи находятся в корзине; наличие хотя бы одной статьи вне корзины оставляет результат вне корзины.
- Каждый вид ручной защиты от правил сохраняется, если он установлен хотя бы у одной статьи; объединение не отменяет ручной unread или восстановление из корзины.
- Время первого поступления результата равно самому раннему из времён объединяемых статей. Обновление и перегруппировка не устанавливают вместо него текущее время.

Эти правила применяются к изменению совпадения по любому полю ключа дедупликации. При объединении сохраняются все связи с источниками и причины автоматических действий. Перегруппировка, перенос состояний и обновление связей публикуются согласованно; устаревшая версия записи вызывает повтор вычисления по актуальным состояниям, а не выбор случайного победителя. Повтор события не создаёт дополнительные записи, повторные отметки или двойные счётчики. Новая связь от точного дубля без самостоятельной библиотечной записи сохраняет все состояния существующей статьи; она не считается отдельной статьёй с пустыми отметками для вычисления описанного объединения. Результаты показываются с соблюдением стабильности списка из §3.1; согласованная граница массовых действий и приоритет новых ручных изменений сохраняются.

Повтор того же ID с теми же данными идемпотентен. **Согласованная политика редакций — `latest_successful`:** обновление того же ID заменяет текущую редакцию только после полного устойчивого сохранения новой; прежняя редакция после безопасной замены удаляется, история редакций не ведётся. Ошибка, усечённый ответ или незавершённая запись не заменяют успешный результат. Исходная запись остаётся одной на пару источник + upstream ID; если её изменение не меняет группировку, библиотечная запись и её состояния сохраняются. При изменении группировки действуют описанные выше правила разделения/объединения; политика хранения редакций не выбирает результат переноса состояний. Устаревшая задача не может откатить уже опубликованную более новую редакцию. Противоречивые дубликаты одного ID в одном ответе не разрешаются случайным last-write-wins: ошибка и доступный для повторной обработки материал сохраняются. Идентификатор revision нужен для конкурентного доступа, идемпотентности и оценки правил, а не для обещания хранения истории.

Исходный URL, URL запроса после разрешения относительной ссылки и конечный URL после redirect хранятся раздельно. Query-параметры не отбрасываются для неявной дедупликации. Fingerprint служит ускорению сравнения и проверяется по исходным данным; коллизия не может уничтожить запись. Дата публикации, дата изменения источником, время обнаружения и время поступления в библиотеку — отдельные поля; отсутствующая дата публикации остаётся отсутствующей.

### 5.2. Автоматический полный текст

Сначала сохраняются доступные метаданные и текст ленты, статья появляется в библиотеке. В фоне выполняется HTTP-загрузка страницы и выделение основного текста. Для JS-страниц используется Chromium по явной политике источника или диагностируемому переходу к browser extraction. Результат содержит читаемый HTML, plain text, сведения об извлечении и ссылку на исходный материал.

**Принято по делегированному пользователем выбору:** повторная загрузка полного текста запускается при обнаружении изменения исходной записи в RSS/Atom/JSON Feed, Web feed или адаптере, а также по ручной команде «Обновить полный текст». Неизменившаяся запись, `304` и изменение только служебного времени опроса не запускают новую загрузку. Повторная доставка того же события не создаёт дублирующих заданий; временные ошибки обрабатываются предусмотренными конфигом ограниченными retry. Периодического переобхода страниц всего архива в v1 нет: правка сайта, не отражённая в исходной записи, обнаруживается при ручном обновлении. Это ограничение показывается в описании функции; время последней успешной загрузки доступно в статье.

Состояния: `queued`, `running`, `ready`, `retry_scheduled`, `blocked`, `failed`. Причина доступна пользователю без внутренних секретов: например ограничение сайта, timeout, неподдерживаемая страница, превышение допустимого размера. Неуспех не заменяет уже сохранённый текст пустотой. Ошибка извлечения не мешает открыть описание из ленты или оригинальную ссылку. Доступны повтор и диагностика источника.

Автоматическая загрузка не зависит от того, открыл ли пользователь статью, прочитал ли её или отправило ли правило её в корзину. Нет отсечения по возрасту, прочитанности или количеству накопленных статей. Успех фиксируется только после устойчивого сохранения полного результата; усечённый ответ не маркируется полным текстом.

HTML внешнего сайта считается недоверенным. Исходный полученный материал хранится как данные, а для чтения создаётся явно отдельное безопасное представление: без исполняемых скриптов, обработчиков событий и активных форм. Это документированная трансформация отображения, а не изменение сохранённого оригинала. Сохраняются версия извлекателя и версия санитайзера. Политика `latest_successful` применяется и к полному тексту: предыдущий полный результат остаётся доступным до устойчивого сохранения и публикации нового. Само обновление метаданных или текста RSS не удаляет уже полученный полный текст; неудача нового извлечения сохраняет его с указанием версии и статуса попытки.

**Согласованная граница архива:** достаточно текста, HTML и метаданных, которые хранятся в YDB; оригинальные изображения, видео, аудио и вложения бессрочно не зеркалируются в v1. Поэтому текст остаётся доступен после исчезновения сайта, но внешняя картинка может пропасть.

Предлагаемый контракт отображения внешних изображений: они загружаются только по явной настройке читателя, через защищённый media endpoint с проверкой принадлежности статьи; произвольный открытый прокси не предоставляется.

### 5.3. Глубина и сбои обнаружения

**Согласовано:** первая загрузка охватывает доступную ленту или явно выбранную глубину Web feed. До создания подписки пользователь видит эту область: доступная лента или выбранное число страниц Web feed. Обнаруженные валидные статьи сохраняются все; ограничение страницы/размера/времени обхода не должно незаметно превращаться в отсечение уже разобранных статей. Если обход остановлен лимитом, виден статус неполного обхода и точка продолжения.

Нельзя обещать получение записей, которые источник удалил из своей выдачи между опросами. Последний успешный опрос, отставание и ошибки доступны в UI. Ответы, необходимые для восстановления уже начатого ingest, сохраняются до фиксации результата; авария между сетевой загрузкой и устойчивой записью не считается успешным получением.

## 6. Визуальный конструктор Web feeds

Обязательный пользовательский путь: «Добавить источник → Web feed» → вставить URL → загрузить страницу → увидеть предложенные группы повторяющихся ссылок → выбрать группу или вручную нажать на пример статьи → увидеть похожие элементы и предпросмотр будущей ленты → задать название и сохранить в текущем пространстве. Это соответствует описанному Inoreader сценарию [Web feeds](https://www.inoreader.com/blog/2025/02/improved-web-feeds-track-changes.html).

В конструкторе доступны включение JavaScript, desktop/mobile viewport, скрытие мешающих overlay/cookie-элементов в предпросмотре и расширенное редактирование CSS/XPath-селекторов. Для извлечения задаются ссылка, контейнер карточки, заголовок, дата при наличии и, опционально, область текста статьи. Для листинга поддерживаются следующая страница, дополнительные стартовые страницы, ограниченное число нажатий «загрузить ещё» и прокруток. Изменение настройки пересчитывает предпросмотр и показывает ошибки, а не молча создаёт пустую ленту.

Предлагаемая реализация preview — screenshot браузерной страницы с безопасным слоем выбора элементов по DOM-геометрии из CDP. В интерфейс приложения не вставляются исполняемый DOM чужого сайта и его JavaScript. Клик в режиме выбора выбирает элемент для рецепта, а не выполняет произвольную транзакцию на сайте. Идентификаторы DOM и координаты привязаны к версии snapshot; после изменения viewport, навигации или перерисовки устаревший выбор отвергается и пересчитывается. Точность сопоставления проверяется техническим прототипом.

Сессия конструктора принадлежит пользователю и пространству, имеет deadline и отдельный browser context. Cookies, localStorage, загруженные файлы и browser profile не разделяются между пользователями. Ввод учётных данных стороннего сайта, сохранение пользовательских cookies, произвольные заголовки авторизации и выполнение введённого пользователем JS отсутствуют.

Сохранённый рецепт версионируется. Плановый сбор использует тот же валидированный рецепт и тот же parser, что и предпросмотр. Изменение рецепта не меняет чужую подписку, не удаляет уже полученные статьи и не сбрасывает их состояния. Рецепты Web feeds по умолчанию принадлежат конкретному пространству; глобально разделяются только явно безопасные неизменяемые определения публичных источников. Экономия сетевых запросов не даёт возможности редактировать чужой рецепт.

Если страница перестала соответствовать селекторам, сайт заблокировал загрузку или больше не отдаёт материалы, источник получает видимый статус. Пустой результат на ранее работающем листинге диагностируется отдельно от сетевой ошибки. Пользователь может открыть конструктор с текущим рецептом и исправить его; система не подменяет источник автоматически.

## 9. Архитектура приложения

```text
Browser пользователя
        │ HTTPS / same-origin API + встроенные static assets
        ▼
┌──────────────── Один Rust binary ───────────────────┐
│ HTTP API · auth · application use cases · scheduler │
│ domain · storage port · collectors · fulltext       │
│ shared outbound policy · CDP adapter · embedded UI  │
└──────────┬───────────────────┬──────────────────────┘
           │                   │ CDP в закрытой сети
           ▼                   ▼
     YDB Serverless       Chromium container
                               │
                     контролируемый сетевой выход
                               ▼
                         публичные сайты
```

Compose запускает и перезапускает оба контейнера. Приложение не управляет Docker daemon и не монтирует `docker.sock`. Node и Rust toolchain нужны при сборке; конечному пользователю приложения достаточно бинаря, конфига, YDB и Chromium для browser-функций.

Предлагаемые границы Cargo workspace:

- `reader-core`: сущности, валидированные ID/scope, правила и storage/browser/fetch порты; без зависимости от Axum, YDB SDK и конкретных сборщиков.
- `reader-application`: пользовательские сценарии, orchestration заданий, авторизация операций и обработка результатов через порты.
- `reader-storage-ydb`: единственная реализация storage port, YQL, транзакции, schema management и инструментация SDK.
- `reader-collectors`: RSS/Atom/JSON Feed, HTML и именованные site adapters на общих HTTP/browser портах; разбиение на отдельные crates только при реальной границе тяжёлой зависимости.
- `reader-web-runtime`: общая outbound policy, HTTP, CDP, безопасное извлечение/preview; тяжёлые библиотеки изолированы здесь.
- `reader-server-contracts`, `reader-server`, `reader-server-ui`: DTO/schema, HTTP transport, встроенные артефакты UI соответственно.
- `reader` binary: CLI и сборка зависимостей; `web/`: Preact features, application ports, HTTP infrastructure adapter, общие UI primitives.

Имена предварительные; направление зависимостей обязательно. Не создаются пустые crates «на будущее». UI features не делают прямые fetch вне HTTP adapter; backend handlers не содержат YQL или обход сайтов. Frontend и backend проверяют одни ограничения на соответствующих границах.

**Согласовано:** архитектура должна быть по возможности модульной. Каждый модуль владеет своей ответственностью и инвариантами, имеет небольшой явный публичный контракт и может проверяться отдельно. Доменные правила, получение/разбор источников, извлечение fulltext, хранение, orchestration заданий и HTTP/UI transport разделяются по ответственности. Site adapters используют общий конвейер через определённые порты; добавление источника не требует копировать инфраструктуру или менять несвязанные adapters. Во frontend отдельные features отвечают за reader, подписки, правила, пространства, auth и Web feed builder, используя общие UI primitives и application/API ports.

Модульность не означает отдельный crate на каждый файл или источник, дополнительные сервисы или интерфейсы без реального потребителя. Выделение crate оправдывается границей зависимостей, ответственности либо стоимости сборки; внутри достаточно обычных модулей. Запрещены циклические зависимости и обращение к приватным деталям соседних модулей. Архитектурные проверки закрепляют направление зависимостей и отсутствие YDB/HTTP/browser-деталей в домене; тестовые fixtures и helpers живут отдельно от production-кода. Изолированные тесты используют порты, а интеграционные проверки подтверждают реальное взаимодействие модулей.

### 9.1. Storage trait

Порт представляет предметные операции, а не универсальное `execute_sql`. Потребитель получает типизированные результаты и ошибки: not found, conflict, invalid input, unavailable, deadline и нарушенный контракт. Все библиотечные операции требуют `NamespaceScope`. Служебные общие операции ingest доступны отдельному внутреннему capability, недоступному из пользовательского HTTP-ввода.

Примеры операций: создать аккаунт с погашением приглашения, создать подписку и начальное задание, идемпотентно сохранить результат ingest и enqueue fan-out, доставить статью в пространство, условно изменить состояние статьи, получить страницу библиотеки, сохранить рецепт с expected revision, захватить/продлить/завершить lease. Это эскиз интерфейса, не требование большого монолитного trait: допустимы узкие subtraits с одной реализацией `YdbStorage`.

Для каждой составной операции документируются атомарность, идемпотентность, границы retry и видимость результата. Замыкания retry базы не выполняют HTTP-запросы и другие внешние побочные эффекты. Не создаются SQLite/PostgreSQL/in-memory backend для приложения или скрытое локальное хранилище при отказе YDB. Для интеграционных тестов используется реальная совместимая YDB; чистые доменные тесты проверяют функции без создания второго database backend.

## 10. Логическая модель данных и YDB

Это модель владения, а не окончательный DDL. Физические ключи, индексы и batch sizes утверждаются после этапа проверки YDB Serverless.

| Сущность | Основные данные и граница владения |
|---|---|
| User, session, invite | Аккаунт, credential verifier, сроки и отзыв сессий, одноразовые приглашения |
| Namespace | Владелец, неизменяемый ID, имя, active/archived; archived обязательно содержит общую валидную причину, автора и время и запрещает доставку всех подписок пространства без перезаписи их индивидуальных состояний |
| Namespace state event | Scope, переход archive/restore, общая причина архивирования, автор и время; история сохраняется после восстановления |
| Source definition | URL/тип/валидированная конфигурация получения; публичное общее либо приватное пространству определение |
| Web feed recipe | Владелец/scope, селекторы, browser actions, настройки, revision |
| Subscription | Scope, source/recipe revision, название, active/paused/archived и cursor доставки; paused обязательно содержит валидную причину, время и инициатора |
| Subscription state event | Scope/subscription, переход pause/resume, исходная причина паузы, время и инициатор; история сохраняет причины после возобновления |
| Article | Исходная запись: источник + upstream identity, URL, метаданные, current revision; без личных read/trash флагов. Несколько исходных записей могут относиться к одной библиотечной статье |
| Content / chunks | Последняя успешная редакция текста ленты и полного текста: исходный материал, безопасное представление, provenance, revision и размер; временные части новой редакции до публикации |
| Library entry | Scope + устойчивый ID библиотечной статьи; ключ дедупликации — точные URL, заголовок и описание (при отсутствии URL — источник + upstream identity); время первого поступления, read/saved/later/trash, ручные overrides, revision |
| Library origin | Устойчивая связь библиотечной статьи с подпиской и исходной Article; сохраняет все источники объединённой статьи |
| Rule / rule evaluation | Scope/subscription, правило и версия применимости, набор версий при доставке или явном массовом запуске, версия входа, результат/причина действия либо отмены; диагностика выполненного действия переживает удаление правила |
| Job / outbox / lease | Тип, scope/capability, payload reference, run_at, попытка, lease token/deadline, cursor и ошибка |
| Import batch / item | Происхождение, результат разбора, назначение, решение о дубликате, прогресс применения |

Библиотечная запись — устойчивое свидетельство, что статья принадлежит пространству. Она не вычисляется заново по текущему списку подписок, иначе отписка потеряет доступ к архиву. Доступ к общему Article/Content всегда проверяется через эту связь. Новая подписка получает явно показанную начальную выборку и последующие поступления; она не получает чужие состояния и не подключает весь общий архив незаметно.

В одном пространстве создание библиотечной записи и привязка источников проверяют уникальность полного ключа дедупликации атомарно: конкурентная доставка одинаковых URL, заголовка и описания из разных лент не создаёт две строки или двойной счётчик. Ограничения уникальности только по URL нет: различающиеся заголовки/описания должны сосуществовать. Fingerprint может ускорять поиск кандидатов, но равенство подтверждается всеми исходными значениями, включая отсутствие полей. Связи с источниками сохраняются при отписке; доступ к вариантам контента ограничен исходными записями, действительно доставленными в это пространство, даже если в backend известен тот же URL из чужой подписки.

Контент, который больше допустимой строки/запроса YDB, хранится частями с manifest. Публикация complete manifest происходит после записи всех частей. Пока запись неполная, прежняя полная версия остаётся читаемой; незавершённая версия возобновляется. Ограничения размеров проверяются до записи и при фактическом чтении потока; превышение отображается как ошибка, а не усечение. Конкретные размеры определяются измерением и документированными лимитами сервиса.

После атомарного переключения текущей редакции прежние части удаляются возобновляемой служебной очисткой, только когда они больше не нужны активным чтениям и незавершённым заданиям. Временное сосуществование редакций обеспечивает безопасную замену, но не создаёт пользовательский архив версий. Очистка не удаляет текущий успешный результат или библиотечную запись.

Архивным статьям, полным текстам, библиотеке и корзине не назначается TTL. TTL/очистка допустимы для истёкших сессий, browser preview и завершённых служебных записей после проверки отсутствия незавершённой работы; это не очистка пользовательского архива. Производные счётчики могут быть восстановлены из первичных данных.

### 10.1. Устойчивые задания

Источник истины очереди и расписания — YDB, без Redis/Kafka. Захват задания атомарен; lease содержит fencing token. Продление и завершение проверяют token и актуальную версию, поэтому запоздавший worker не публикует результат после передачи задания другому. После аварии просроченное задание становится доступно; graceful shutdown перестаёт брать новые задания и даёт текущим завершиться в заданный срок.

Гарантия обработки — at least once с идемпотентным логическим результатом. Сохранение статьи и факт необходимости fan-out согласованы транзакционно либо через устойчивый outbox. Доставка многим подписчикам выполняется ограниченными возобновляемыми порциями, без одной транзакции на всех пользователей. Запись library entry и первичных состояний не дублируется при retry. Долгие сетевые операции происходят за пределами транзакций.

Начальное развёртывание — один экземпляр приложения; корректность lease не должна зависеть от единственности процесса. Пользовательские preview и чтение имеют отдельный бюджет ресурсов, чтобы отставание автоматического сбора не делало UI недоступным. Есть очереди/лимиты для feed, browser, fulltext и fan-out; никакой бесконечной очереди в памяти вместо durable jobs.

### 10.2. Заглушка поиска

**Согласовано:** полноценный поиск отложен за пределы первой версии. В навигации остаётся видимый неактивный пункт `Search` с постоянной подписью `Coming later` и доступным описанием недоступности. Заглушка не содержит редактируемого поля, не принимает запрос и не изображает результаты или состояние «ничего не найдено». Для неё не назначается горячая клавиша. Её размер и положение соседних controls стабильны.

В v1 не создаются поисковые API, операции storage port, таблицы/индексы, фоновые задания, настройки или метрики поиска. Показ заглушки и взаимодействие с ней не запускают поисковые запросы к backend/YDB. Полный текст продолжает загружаться и сохраняться для чтения и правил; обычные списки, фильтры подписки/состояний/времени и корзина сохраняют свои контракты.

Семантика совпадений, языки/токенизация, индекс, ранжирование и производительность будущего поиска проектируются отдельной задачей. Они не являются открытыми вопросами или техническими блокерами v1; конкретный контракт и способ реализации пока не выбраны.

### 10.3. Обязательная техническая проверка до основного backend

На отдельной тестовой YDB Serverless проверить выбранную версию Rust SDK, авторизацию/обновление credentials, discovery, параметризованные запросы, транзакционные конфликты и retry, конкурентный lease, размеры текста/chunks, keyset pagination и индексы для списков, дедупликации и заданий. Официальный [пример Rust SDK](https://ydb.tech/docs/en/dev/example-app/rust/) является отправной точкой, но не результатом теста на целевом окружении.

Результат — записанные измерения RU, задержки и объёма для realistic seed и синтетического архива, выбранные версии/DDL и список ограничений. Нужны endpoint, database path и отдельные сервисные credentials с минимальными правами. На момент спецификации этих проверок нет; облачные ресурсы не создавались и стоимость не подтверждена.

## 11. Сеть, браузер и недоверенный контент

Вся загрузка пользовательских URL проходит одну outbound policy: только явно поддерживаемые HTTP(S), проверка URL, DNS и фактического адреса соединения, запрет local/private/link-local/metadata адресов, корректная проверка IPv4/IPv6 и адресных представлений. Решение DNS связывается с фактическим соединением, чтобы не оставить DNS-rebinding между проверкой и подключением.

Redirect разрешён, но каждый hop, включая same-origin, проходит проверку заново. Заданы общий deadline и максимальное число переходов; loop, запрещённая цель и превышение лимита возвращают типизированную ошибку. Между origin не передаются credentials, чувствительные заголовки и request body. Подписка на HTTP-источник показывает незашифрованный transport и требует явного выбора; URL не переписывается в HTTPS автоматически.

Те же гарантии распространяются на Chromium: документы, iframe, subresources, fetch/XHR, WebSocket и новые окна не получают обход политики. Проверить только исходный URL недостаточно. Предлагается закрытая сеть браузера и контролируемый HTTP(S) egress через компонент того же Rust-приложения, дополненный CDP-проверками URL и заголовков. Прямой выход браузера в интернет, внутреннюю сеть, к UI/API приложения и metadata должен быть запрещён сетевыми правилами. Внутренние CDP и proxy доступны только нужным контейнерам. Конкретная proxy/ACL-схема проверяется прототипом до открытия Web feeds пользователям; fail-open недопустим.

Конфигурационные обращения к YDB и инфраструктурной авторизации используют отдельный доверенный профиль: адреса задаёт оператор, а не пользовательский URL. Разрешения этого профиля нельзя унаследовать для статьи или браузерного запроса. Одинаковая инструментация сохраняется и для SDK, и для HTTP. Секреты, query string, cookie, тела статей и сырые ошибки SDK не попадают в общие логи.

Chromium не публикует CDP-порт наружу, работает без пользовательских credentials и без монтирования директорий хозяина. Ресурсы CPU/RAM, число contexts/pages, срок preview, время навигации, объём ответа, число действий и скачиваний ограничены валидированным конфигом. Загрузки файлов, произвольные протоколы и доступ к `file://` не предоставляются. Старое `browser_no_sandbox: true` из Go-конфига не копируется автоматически: изоляция контейнера и browser sandbox проверяются для выбранного образа.

Веб-интерфейс использует CSP и безопасный renderer. XML-парсинг лент не разрешает внешние сущности; HTML, OPML, URL, selector и импортируемый JSON/YAML валидируются как недоверенный ввод. Ошибка одной записи сохраняется в отчёте; частичный результат не маскируется под полный успех.

## 12. Конфигурация, сборка и эксплуатация

### 12.1. Конфигурация

Предлагаемый CLI: `inoreader --config /etc/inoreader/config.yaml serve`. Тот же бинарь предоставляет команды проверки конфигурации, подготовки схемы, bootstrap-admin и dry-run/apply начального manifest. Точные имена команд фиксируются при каркасе; дополнительных executable с бизнес-логикой не требуется.

| Группа конфига | Что задаётся |
|---|---|
| `server` | bind address, внешний origin, trust policy reverse proxy, сроки запросов и graceful shutdown |
| `database.postgres` | host, port, database, user, password-file reference, connection-pool size and acquire deadline |
| `database.migration_source_ydb` | read-only source endpoint, database path, credential reference and bounded retry settings used only by the one-way migration command |
| `auth` | параметры password hashing, session lifetime, invite/reset lifetime, лимиты попыток |
| `http` | user agent, connect/request deadlines, redirect hops, body/decompression limits, допустимая политика HTTP |
| `scheduler` | polling intervals, lease/renewal, workers, per-origin limits, очередь retry и максимальный возраст попытки |
| `subscriptions` | `pause_reason_max_bytes`: общий максимальный размер обязательной причины индивидуальной паузы или архивирования пространства в UTF-8 байтах |
| `browser` | CDP endpoint, contexts/pages, timeout, viewport profiles, action limits и egress profile |
| `ingest` | глубина первичной загрузки, страницы/статьи в одной порции работы, размер входных данных и журнал ошибок |
| `content` | явно заданная политика `version_policy: latest_successful`, chunk sizing, лимиты извлечения и media proxy |
| `observability` | logging, metrics, сбор длительности внешних операций и диагностические budgets |

Все влияющие на безопасность, ресурсное потребление и остановку обработки лимиты явные, документированные и валидируемые. В итоговом `config.example.yaml` должны быть конкретные проверенные значения с единицами, а не неописанные константы в коде. Здесь они не объявляются измеренными. Недопустимый конфиг завершается ошибкой до запуска workers; поля не исправляются догадками и неизвестные поля не игнорируются.

`content.version_policy` обязателен без неявного значения по умолчанию: `latest_successful` явно закрепляет согласованную замену и удаление прежних редакций. Политика документируется в конфиге и диагностике; её отсутствие или неподдерживаемое значение отклоняются до запуска workers.

Секреты передаются через environment/file/provider references, не входят в репозиторий и не показываются целиком в диагностике. Настройки пространства, подписки, рецепты и правила живут в PostgreSQL и меняются через UI; YAML не превращается во второй конфликтующий источник их истины. YDB остаётся только источником проверяемой одноразовой миграции и резервным снимком на период отката. Изменение операторского конфига в v1 требует перезапуска; hot reload не обещается.

### 12.2. Один бинарь

Frontend собирается esbuild и включается в изолированный UI crate через compile-time assets, как в референсном проекте. HTML, JS, CSS и необходимые локальные ресурсы доступны из бинаря; runtime не читает исходный `web/` или `node_modules`. Cache policy различает HTML и контентно-адресованные assets, чтобы клиент не смешивал несовместимые версии UI/API.

Изменение только backend не запускает без необходимости пересборку всего UI. API/schema generation — отдельная явная команда; сборка потребляет артефакты и обнаруживает устаревший контракт, не переписывая рабочее дерево. Cargo.lock и package-lock фиксируют версии; toolchain, profiles и sccache setup соответствуют правилам референсного проекта.

Проверка поставки: собрать release artifact в чистом окружении, перенести один бинарь в отдельную директорию без исходников и Node, запустить с тестовым конфигом и проверить UI, API и операции с YDB. «Один бинарь» относится к приложению; согласованные YDB и Chromium остаются внешними runtime-зависимостями. Статическая линковка под все платформы отдельно не обещается; основной deployment target — Linux, конкретная архитектура зависит от сервера.

### 12.3. Запуск и отказоустойчивость

Production Compose содержит app и Chromium с health checks, restart policy, resource limits и закрытыми служебными портами. YDB Serverless расположена вне Compose. Для локальных integration/E2E проверок допустим отдельный профиль с настоящей YDB: это тот же backend, а не вторая реализация storage. TLS завершается в уже имеющемся reverse proxy либо в отдельно выбранной конфигурации размещения; обязательный третий контейнер в согласованную схему не добавляется молча. Внешний origin и доверенные proxy задаются явно.

`live` проверяет живость процесса; `ready` — способность обслуживать основной API и корректную схему YDB. Недоступность браузера отражается как degraded capability и задерживает browser jobs, но RSS и чтение сохранённых статей продолжают работать. Недоступность YDB не приводит к фиктивно успешному сохранению или переходу на память/файлы. Задания остаются в устойчивом состоянии; пользователь получает понятную ошибку.

Наблюдаемость включает длительности всех внешних запросов, ошибки/last success источников, lag очередей, attempts, занятые leases, размер/возраст очереди полного текста, активные browser contexts, объём архива и доступные метрики стоимости YDB. Логи структурированы, с correlation IDs; не содержат пароли, сессионные токены, полные секретные URL и содержимое пользовательских статей.

Бессрочное хранение увеличивает расходы. В первой версии нужны измерение роста, видимость накопленного объёма и уведомление оператору о достижении заданных бюджетов; превышение бюджета не запускает автоматическое удаление. При нехватке ресурсов приостанавливается приём новой работы с явным статусом, уже сохранённый архив остаётся целым.

До начала реального накопления настроить поддерживаемый целевой YDB способ резервного копирования и проверить восстановление в отдельную базу. Такой backup не является вторым online storage backend приложения. Изменения схемы выполняются контролируемой процедурой с проверкой версии и сохранением пользовательских данных. Правило проекта об отсутствии backward compatibility не разрешает сбрасывать бессрочный архив: допустима одноразовая конверсия без сохранения старых runtime-API; неподдерживаемая схема останавливает запуск, а не пересоздаётся разрушительно.

## 13. Проверки и критерии приёмки

### 13.1. Политика проверки репозитория

В обычной разработке используется **`just check-affected`**: package-scoped `cargo check` и `tsc --noEmit` для затронутого frontend. По унаследованному `AGENTS.md` это compile-only gate; он не запускает тесты, lint, rustfmt, bundling, Docker/E2E и release build. При неясном scope используется `just test-affected-dry`.

Тесты и fixtures ниже должны быть написаны вместе с соответствующими контрактами; их запуск и полный release gate выполняются в отдельно разрешённой фазе полной проверки/release. Наличие compile-only результата нельзя выдавать за доказательство runtime-изолированности или рабочей поставки. Полная приёмка включает реальные YDB и Chromium; отсутствие инфраструктуры отмечается как непроверенная часть, а не успешный skip. Для этой документационной задачи сборки и тесты приложения не требуются.

### 13.2. Обязательная глубина тестового покрытия

**Согласовано:** тестирование — существенная часть реализации первой версии. Нужен плотный набор содержательных автоматизированных проверок, а не только smoke-тесты или happy path. Тесты и fixtures добавляются вместе с каждой функцией и исправлением; покрывают успешные сценарии, границы, невалидный ввод, ошибки, конкуренцию, retry/restart и сохранность данных там, где это применимо. Для A01–A31 ведётся соответствие «контракт → тесты → результат последнего разрешённого запуска → непроверенные случаи». Метрики покрытия помогают находить пробелы; число тестов, процент строк и snapshots сами по себе не доказывают выполнение контракта.

**Данные каждого известного источника.** Проверяемый inventory из §7 служит реестром покрытия: все 42 source IDs `personal_feed`, все подтверждённые источники из PDF с ожидаемыми 214 строками и каждый последующий добавленный источник. Пересечения явно сопоставляются; общий adapter не заменяет проверки на данных каждого относящегося к нему источника. Для каждого поддержанного источника сохраняются репрезентативные реальные RSS/Atom/JSON Feed, HTML листинга/статьи, ответы публичного API и, где нужно, DOM/сетевые fixtures динамической страницы. У набора указаны источник, дата получения, происхождение, версия рецепта и явно проверенные ожидаемые записи/поля. Секреты и приватные данные в fixtures не включаются; искусственные повреждения хранятся как отдельные, явно обозначенные варианты.

Проверки воспроизводят production-путь получения/разбора/извлечения на сохранённых данных и сверяют идентичность, исходные URL/заголовки/описания, отсутствие и пустые значения, Unicode, даты, пагинацию, полный текст, повторную обработку и обновления — по возможностям источника. Набор должен обнаруживать пустой результат из-за сломанного selector, пропущенную страницу, потерю/усечение полей и неправильное объединение статей. Для характерных отказов добавляются fixtures повреждённого ответа, изменения разметки, частичного результата, сетевой ошибки или блокировки. Ожидаемые результаты проверяются по исходным данным и контракту, а не автоматически принимаются из текущего вывода parser. Новый источник без fixtures и проверок не считается завершённой интеграцией; изменение adapter прогоняется на корпусе всех использующих его источников в разрешённой фазе проверки.

Основной регрессионный корпус воспроизводим и не зависит от текущего состояния публичных сайтов; live-проверки источников выполняются отдельно и не заменяют его. Недоступный источник остаётся в inventory с причиной и явным пробелом покрытия: проверка корректного сообщения о блокировке не доказывает успешное извлечение. Если достоверные данные получить нельзя, не подменять их выдуманным успешным fixture и не считать покрытие полным. Это отражается в отчёте приёмки, без молчаливого пропуска.

**UI.** Компонентные и интеграционные тесты Preact/Vitest/Testing Library покрывают все экраны и пользовательские действия, их загрузку, пустое состояние, успех и ошибку; переходы между пространствами, read/unread, saved/later, корзину, массовые действия, подписки, обязательные причины pause/archive, правила и preview, OPML, auth и Web feed builder. Обязательны проверки приоритета ручных действий, сохранения ввода при ошибке, восстановления фокуса, клавиатуры, доступных подписей, auth-autofill и защиты обычных полей. Асинхронные сценарии явно управляют задержками и порядком ответов; проверяют немедленный pending, защиту от двойной активации и отсутствие применения устаревшего ответа после переключения контекста. Snapshots дополняют проверки поведения, а не заменяют их.

**Реальный браузер.** В автоматизированную приёмку входит браузерный набор; предлагаемый инструмент — Playwright с закреплённой версией и браузерными зависимостями. Компонентная среда jsdom не является доказательством корректной геометрии, фокуса и поведения реального браузера. Браузерные тесты проходят основные пути пользователя от входа до чтения, настройки правил, pause/archive/restore, импорта и создания Web feed; проверяют перезагрузку страницы и устойчиво сохранённые состояния. E2E используют настоящий backend и совместимую YDB, а browser-backed сборщики — реальный Chromium. Изолированные UI-тесты с управляемыми ответами API разрешены как отдельный слой и не выдаются за E2E всего приложения.

В браузере проверяются desktop/mobile viewport, светлая/тёмная тема, длинные и многоязычные данные, мышь и клавиатура. Для асинхронных обновлений, раскрывающихся блоков, ошибок и уведомлений измеряется положение окружающих интерактивных элементов до/во время/после изменения; отдельно воспроизводится повторный click при задержке ответа. Непредвиденный сдвиг цели, пропавший focus, повторная отправка и отсутствие немедленного feedback — регрессии. Визуальные сравнения ключевых экранов дополняют эти проверки; эталоны не перезаписываются автоматически ради зелёного результата. При сбое сохраняются диагностические trace, screenshot и относящиеся к сценарию безопасные логи. Фиксированные sleep и retry до случайного успеха не заменяют ожидание наблюдаемого состояния; нестабильные тесты не скрываются молчаливым skip.

**Интеграция и организация запусков.** Помимо UI и источников покрываются границы модулей, валидированные конструкции/десериализация, изоляция scope, транзакции и lease, частичное сохранение, retry/restart, сеть/redirect/SSRF, недоверенный HTML и backup/restore. Тестовые данные и состояние изолируются между сценариями; воспроизводимые fixtures, сервисные образы и версии инструментов фиксируются. Быстрые доменные/компонентные проверки, корпус источников, интеграционные и браузерные E2E оформляются отдельными явно запускаемыми наборами в CI/release. Все обязательные наборы входят в полную приёмку, а недоступная инфраструктура означает непроверенный результат. Это требование к составу тестов и последующей приёмке сохраняет compile-only контракт `just check-affected` из §13.1.

### 13.3. Проверяемые сценарии

| ID | Сценарий и ожидаемый результат |
|---|---|
| A01 | Чистая сборка даёт один app binary; из пустой runtime-директории без Node и UI-исходников открываются интерфейс и API |
| A02 | Неверный конфиг, отсутствующий secret и несовместимая схема дают диагностируемую startup error до запуска workers, без изменения данных |
| A03 | Пользователь регистрируется только по приглашению, входит, выходит и меняет пароль; открытая регистрация недоступна. Сброс выполняется по одноразовой ссылке администратора без email-сервиса. Повторное погашение приглашения/ссылки сброса и использование отозванной сессии отвергаются. Собственные auth-формы поддерживают автозаполнение логина/пароля через типизированный `AuthField`; компонентные проверки подтверждают роли и невозможность переопределить их атрибуты, architecture guard запрещает применение исключения в редакторах. ## 14. Порядок реализации после утверждения спецификации

1. **Технические прототипы и решения.** Проверить реальную YDB Serverless/Rust SDK и защищённый Chromium preview/egress. Подготовить source inventory и выявить неподдерживаемые источники. Зафиксировать выводы до дорогой реализации зависящих от них компонентов.
2. **Каркас и контракты.** Перенести Preact/toolchain/lints/gates и применимые UI primitives референсного проекта, привязать AGENTS к архитектуре читалки, собрать embedding UI, config/CLI, storage port/YDB adapter и версионирование схемы.
3. **Вертикальный срез.** Аккаунты, пространства, одна обычная лента, чтение, состояния, корзина, durable scheduler и сохранение после restart. Сразу проверить границы владения и транзакционные контракты.
4. **Полезная библиотека.** Автоматический fulltext, бессрочный архив, UI-заглушка поиска по §10.2, массовые действия, простые правила, OPML и responsive/keyboard UX.
5. **Web feeds и источники.** Визуальный конструктор, динамические страницы, порт активных `personal_feed` adapters, исправление рецептов из UI, dry-run и применение начального manifest владельца.
6. **Развёртывание и полная приёмка.** Production Compose/config, TLS выбранного окружения, метрики, backup/restore, разрешённые runtime/E2E/security проверки, полный корпус источников, компонентные и браузерные UI-наборы по §13.2 и проверка одного release binary по A01–A31. До этого этапа не заявлять полную готовность сервиса.

Каждый этап оставляет проверяемый результат и перечень ещё не пройденных критериев. Тесты и fixtures разрабатываются на соответствующих этапах вместе с функциями, а не откладываются целиком до финальной приёмки; модульные границы и инфраструктура тестов закладываются в каркасе. Не добавляются новые функции Inoreader просто потому, что они обнаружены в его интерфейсе.

### 15.1. Итог продуктового интервью

Известных существенных открытых продуктовых вопросов для первой версии не осталось. Пользователь подтвердил финальный пакет: явное открытие отмечает прочитано; saved/later независимы; правила сопоставляют буквальную подстроку без учёта регистра; первая загрузка ограничена доступной лентой или явно выбранной глубиной Web feed; регистрация по приглашениям, сброс пароля через администратора. Дополнительно согласованы плотное покрытие данными каждого известного источника, компонентные и браузерные UI-тесты, по возможности модульная архитектура (§9, §13.2), отдельная навигация по подпискам и абсолютная межпользовательская изоляция при допустимом общем fetch публичного URL (§3.3).

Интервью и спецификация завершены. Реализация, импорт начальных источников и развёртывание выполняются отдельным последующим этапом; согласование продуктовых решений не является подтверждением выполненных технических проверок.

| Неподдерживаемые seed URL / блокировки сайтов | Проверяемый inventory и отчёт; сохранить запись об источнике, не объявлять блокируемый источник рабочим |
| Сервер, домен, TLS, регион, архитектура CPU | Конкретизировать перед deployment; они не установлены этим документом |
| Начальный администратор и приглашения | Credentials вводятся при bootstrap; открытая регистрация и email-инфраструктура не требуются |
| Бессрочный рост и стоимость | Измерять, предупреждать, применять backpressure; не вводить скрытый TTL или `max_items` |
