## Что установлено

Проверены все 48 активных подписок, которые в момент снимка удовлетворяли production-условию `consecutive_failures >= 3 || incomplete`. Выполнены повторные публичные HTTP-проверки из локальной сети и с сервера, просмотрены правила извлечения, RSS/XML, исходный код обработки ошибок и состояние очереди. Подписки и конфигурация приложения в этом исследовании не менялись.

- У **всех 48** на момент проверки нет задач сбора в состояниях ready/leased. Исчерпанные попытки остались в failed. Поэтому красный статус не доказывает, что сайт недоступен сейчас.
- **11 ошибок идентичности записей**: 10 HTML-источников и RSS Yandex Cloud. Прокси не устраняет их причину.
- В отдельной проверке curl с сервера **18 из 48** URL полностью ответили HTTP 200. Это не означает, что production-парсер и дальнейший сбор уже исправны.
- Из локальной сети **37 из 48** URL ответили 200. У 19 из них серверная проверка не завершилась успешным получением тела. Сравнение обосновывает проверку другого сетевого маршрута, но не доказывает именно блокировку страны: могли повлиять IP, TLS-клиент, DNS, антибот и временная доступность.
- У старых Medium-адресов Lauren Balik и Alibaba Tech выявлены также 404. Смена IP не исправит неверный адрес.

## Самый практичный порядок действий

1. Исправить возобновление сбора: после обычной серии повторов источник должен получать редкую контрольную попытку. Для 429/503 учитывать Retry-After, для временных сбоев — backoff с jitter; не повторять пять раз за несколько секунд, после чего останавливаться навсегда. Сохранять последнее успешное содержимое и понятную причину ошибки.
2. Исправить 10 HTML-рецептов и отдельно решить контракт полностью одинаковых повторов Yandex Cloud. Широкие селекторы часто выбирают картинку, заголовок и featured-копию одной статьи. Не уменьшать архив до нескольких карточек только ради исчезновения ошибки.
3. Заменить ненадёжное HTML-извлечение проверенными официальными RSS там, где они есть. Перед заменой сопоставить идентификаторы с уже сохранёнными статьями.
4. Бесплатно протестировать внешний выход на небольшой группе: Medium, AWS, Meta, Skyvia, Devart, CData. После доказанного результата выбрать постоянный маршрут.
5. Отдельно подключить Telegram/Zhihu-адаптеры, официальный Reddit OAuth и при необходимости YouTube Data API. У этих источников есть требования помимо доступности TCP/HTTPS.

Cloudflare WARP можно рассматривать как сетевой эксперимент, но не как гарантированный зарубежный прокси: Cloudflare сообщает, что выходной IP отражает приблизительное местоположение пользователя. Поэтому это не основной вариант для географически зависимых блоков. [Документация WARP](https://developers.cloudflare.com/warp-client/known-issues-and-faq/).

Оценка трафика для выбора бесплатного плана: 15 лент × 24 опроса/сутки × 50 KB × 30 дней ≈ 0.54 GB/месяц. При 200 KB уже ≈ 2.16 GB. Это расчётный пример, не замер текущего потребления; полные тексты, картинки и браузерные ресурсы добавляют трафик. Использовать ETag/Last-Modified, разумный интервал и отдельно считать байты каждого маршрута.

## Telegram, Zhihu, Reddit и YouTube

**Telegram.** У RSSHub есть `/telegram/channel/:username`; по умолчанию он читает `t.me/s`, а с Telegram-сессией может использовать Telegram API. Для наших двух публичных каналов web-preview локально работает, поэтому отдельный Telegram-аккаунт пока не обязателен. MTProto-прокси из прежнего обсуждения нельзя вставить как HTTP-прокси для RSS: это другой протокол. Бот получает сообщения только доступных ему чатов/каналов и не является универсальным способом чтения чужих каналов. [Реализация RSSHub](https://github.com/DIYgod/RSSHub/blob/master/lib/routes/telegram/channel.ts), [Telegram Bot FAQ](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get).

**Zhihu.** RSSHub содержит адаптеры Zhihu, но наличие маршрута не гарантирует обход 403. Для пользователей и организаций могут отличаться API/маршруты; обязательна проверка с актуальной разрешённой сессией. Не считать китайский прокси достаточным решением. [Код адаптеров](https://github.com/DIYgod/RSSHub/tree/master/lib/routes/zhihu).

**Reddit.** Официальная документация требует OAuth и рекомендует уникальный описательный User-Agent. Для подходящих приложений с бесплатным доступом указано 100 запросов/минуту на OAuth client id; доступ запрашивается отдельно. К публичным RSS эту квоту приписывать нельзя. Интеграция также должна учитывать правила удаления контента площадки. [Официальная Data API Wiki](https://support.reddithelp.com/hc/en-us/articles/16160319875092-Reddit-Data-API-Wiki).

**YouTube.** Все пять проблемных channel_id локально вернули Atom с 15 видео; два работают и с сервера. Резервный путь: получить uploads playlist через channels.list, затем playlistItems.list, а не search.list. Официальный API требует проект/ключ для публичных данных; действующая документация указывает 10 000 units/day для общей группы остальных методов, а playlistItems.list стоит 1 unit. Для пяти каналов с почасовым опросом это примерно 120 units/day плюс получение метаданных; начальный исторический обход стоит дополнительно. [Обзор API](https://developers.google.com/youtube/v3/getting-started), [playlistItems.list](https://developers.google.com/youtube/v3/docs/playlistItems/list).

## Как встроить в существующую инфраструктуру

Рекомендуемая схема: `планировщик → штатный сборщик → профиль выхода → исходный сайт → проверка/парсинг → PostgreSQL`. RSSHub или внешний browser-fetcher — отдельные адаптеры для сайтов, которым мало общего RSS/HTML-режима.

1. Ввести явные профили выхода: direct, внешний CONNECT/SOCKS, при необходимости SG/HK и отдельный browser. Профиль выбирается для источника/домена; он не должен автоматически менять URL, язык, автора или идентичность статьи. Секрет прокси хранить отдельно от URL и логов.
2. Реализовать выбор транспорта в общем OutboundHttpClient. Сейчас reqwest-транспорт привязывает соединение к проверенному IP и выключает автоматические redirect; браузерные запросы также проходят общую проверку. Глобальный HTTPS_PROXY или флаг только в Chromium не считаются готовой интеграцией: надо сохранить проверку каждого redirect, DNS/IP, TLS/SNI и запрет утечки credentials на другой origin. Для proxy DNS нужен отдельный проверенный контракт, чтобы proxy не обходил SSRF-защиту.
3. Для RSSHub предпочтительна собственная инсталляция с рабочим выходом и кэшем. Private Docker-host адрес сейчас нельзя просто передать как пользовательский feed URL: общий HTTP-клиент блокирует приватные адреса. Нужен отдельный доверенный adapter endpoint/порт либо защищённый публичный HTTPS endpoint; нельзя глобально разрешать private/LAN destinations.
4. Восстанавливать сбор автоматически: после исчерпания коротких повторов назначать редкую контрольную попытку; различать 429/Retry-After, временный TLS/5xx, неправильный URL и дефект парсинга. Показывать время последней попытки и следующей, а не только Needs attention.
5. Метрики по каждой попытке: профиль выхода, стадия DNS/connect/TLS/TTFB/body, HTTP-код, длительность, количество полученных/разобранных/сохранённых записей, bytes и следующий retry. Без токенов, cookies, URL query и тел в логах.
6. Исправление дублей проверять на сохранённых HTML/RSS: количество уникальных статей не должно уменьшаться из-за выбора маленькой витрины. Если вводится политика объединения идентичных RSS-повторов — только явная настройка; различающиеся записи с одним ID должны оставаться диагностируемым конфликтом.

Кодовые основания: [transport](/Users/timmyb32r/cursor/inoreader/crates/reader-web-runtime/src/reqwest_transport.rs), [общая HTTP-политика](/Users/timmyb32r/cursor/inoreader/crates/reader-web-runtime/src/network.rs), [контракт браузерных запросов](/Users/timmyb32r/cursor/inoreader/crates/reader-web-runtime/src/browser.rs), [исчерпание повторов](/Users/timmyb32r/cursor/inoreader/crates/reader-ingest/src/engine/mod.rs), [failed-состояние очереди](/Users/timmyb32r/cursor/inoreader/crates/reader-storage-postgres/src/ingest_store/queue.rs).
