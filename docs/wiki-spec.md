# Изолированная Markdown-вики — согласованная спецификация

Статус: согласовано пользователем и реализовано. Проверки и выкладка отслеживаются в [журнале реализации](tasks/wiki-implementation.md).

## Цель

Встроить в Reader простую приватную вики: страницы с Markdown, внутренние ссылки,
история, поиск и независимые неймспейсы с явной выдачей доступа существующим
пользователям. Хранить страницы, историю, права и привязки в PostgreSQL.

## Согласованные решения

- Каждый пользователь может создавать собственные неймспейсы. У каждого один
  владелец; только он управляет доступом. Глобальная роль администратора Reader
  сама по себе не открывает чужое содержимое вики.
- Владелец выдаёт пользователю роль читателя или редактора отдельно в каждом
  неймспейсе. Читатель читает; редактор создаёт, изменяет, переименовывает, удаляет
  в корзину и восстанавливает страницы.
- Внутренние ссылки и поиск работают только внутри текущего неймспейса.
  Между неймспейсами нельзя создавать внутренние ссылки, даже при доступе к обоим.
- `[[Название]]` указывает на страницу текущего неймспейса. Несуществующая страница
  не создаётся при сохранении ссылки. Редактор открывает ссылку, получает форму
  создания и сохраняет новую страницу. Читателю показывается отсутствие страницы,
  без редактора и без возможности создать её через API.
- Редактор — Markdown с предпросмотром. Без визуального редактора и вложений.
- История хранит автора, время и версию. Восстановление старой версии создаёт новую
  запись, не переписывает и не удаляет историю.
- При одновременном редактировании второй автор получает конфликт и сравнение
  версий. Его черновик не теряется; автоматической перезаписи или слияния нет.
- Удаление обратимое: корзина внутри неймспейса, история сохраняется. Читатели
  удалённые страницы не видят. Окончательное удаление не входит в первую версию.
- Переименование сохраняет старое имя как перенаправление внутри того же неймспейса.
- Одна подписка может иметь одну привязанную вики-страницу; к одной странице могут
  быть привязаны несколько подписок. Привязка не копирует статьи в вики.
- Автоматическое создание страниц по подпискам или статьям отменено. Пользователь
  сам создаёт страницу и затем привязывает её в настройках подписки.
- Доступ к вики не открывает подписки, статьи или сведения о приватных привязках.

## Предлагаемый интерфейс

В основной навигации Reader добавить `Wiki`: полноценный раздел для чтения и
редактирования, а не плавающее окно. В свёрнутой панели остаётся доступная кнопка.
При первом входе — список своих и явно доступных неймспейсов и `New namespace`.
Общий экран показывает только контейнеры, без сквозного поиска по их содержимому.

После выбора неймспейса:

```text
Основная          Страницы текущего          Текущая страница
навигация         неймспейса
                  ┌──────────────────┐       ┌──────────────────────────────┐
Home              │ Engineering  ▾   │       │ Apache Kafka     Edit  ⋯    │
Feed              │ Search pages…    │       │                              │
Wiki              │ + New page       │       │ Markdown-содержимое          │
                  │                  │       │ со ссылками [[...]]          │
                  │ Apache Kafka     │       │                              │
                  │ CDC              │       │                              │
                  │ PostgreSQL       │       │                              │
                  │                  │       │                              │
                  │ Trash            │       │                              │
                  │ Access           │       │                              │
                  └──────────────────┘       └──────────────────────────────┘
```

- На странице основная кнопка только `Edit`; в меню — `History`, `Rename`,
  `Move to trash`, с учётом роли. Заголовок страницы и текущий неймспейс видны всегда.
- `Access` доступен только владельцу; `Trash` — владельцу и редакторам.
- Редактирование: поле названия, Markdown и предпросмотр рядом на широком экране;
  переключатель `Write / Preview` на узком. Фиксированные `Save` и `Cancel`,
  постоянное место для статуса сохранения и ошибок.
- История — список версий и сравнение выбранной версии с текущей. Восстановление
  требует подтверждения. Конфликт редактирования показывает исходную версию,
  актуальную версию и собственный черновик; новый текст сохраняется явно.
- Настройки подписки: строка `Wiki page` с выбором доступного неймспейса и страницы,
  затем `Open`, `Change`, `Unlink`. Выбор страницы не создаёт её автоматически.
- Открытие страницы из подписки сохраняет адрес возврата; Back возвращает в ту же
  подписку. Отвязка не удаляет страницу, а удаление подписки не удаляет вики.
- Переход между неймспейсами — явное действие селектора, не вики-ссылка.
- Переиспользовать cool slate + teal, темы, иконки, защищённые поля, AsyncButton,
  ModalDialog и StatusRegion из существующего UI. Стабильные размеры, мгновенное
  pending-состояние, блокировка повторной отправки; никаких сдвигающих форму тостов.

## Предлагаемые контракты первой версии

### Имена и ссылки

- Страница имеет неизменный ID. Имя — пользовательский текст, сохраняемый точно,
  без скрытого trim, изменения регистра, транслитерации или подстановки slug.
- Уникальность имени и старых имён — в пределах одного неймспейса, с учётом регистра.
  В разных неймспейсах одинаковые имена допустимы и не связаны между собой.
- Пустые имена, переводы строк и разделители синтаксиса `[[...]]` отклоняются явно.
  Точные ограничения длины задаются конфигурацией и проверяются до сохранения.
- В первой версии достаточно `[[Название]]`; шаблоны MediaWiki, категории,
  трансклюзии и специальный синтаксис ссылок между неймспейсами не поддерживаются.
- Алиас указывает сразу на ID страницы, а не на другой алиас: циклы невозможны.
  Существующий текст страниц при переименовании не переписывается.
- Имена страниц в корзине и их алиасы остаются занятыми, чтобы старые ссылки не
  начали вести на новый, посторонний документ. При восстановлении конфликт имени
  не решается молча; конфликт или повреждение состояния выдаётся явно.
- Обычные Markdown-ссылки на маршруты этой вики проходят ту же проверку неймспейса:
  альтернативный синтаксис не должен обходить запрет на внутренние связи.
  Это не запрет скопировать текст человеком между двумя доступными ему областями.

### Markdown и поиск

- Поддержать заголовки, абзацы, списки, цитаты, выделение, код, таблицы, обычные
  ссылки и `[[...]]`. HTML и скрипты не исполняются. Исходный Markdown сохраняется
  точно; безопасное представление — отдельный результат рендеринга.
- Не загружать автоматически внешние изображения, iframe и другие встраиваемые
  ресурсы. В первой версии нет загрузки файлов или редактора изображений.
- Поиск — по имени и тексту текущей опубликованной версии, только в выбранном
  неймспейсе. История, личные черновики, корзина и другие неймспейсы исключены.
- Предлагаемый простой контракт поиска: буквальный текст без учёта регистра,
  без операторов SQL/regex. Результаты с коротким безопасным фрагментом и пагинацией.
  Проверить русский, английский и китайский текст; не изменять оригинал ради индекса.
- PostgreSQL обеспечивает поиск; отдельный поисковый сервис не нужен. Выбор индекса
  подтвердить EXPLAIN и измерениями, не читать все страницы на каждый поиск.

### Черновики и изменения

- Приватный черновик редактора хранится в PostgreSQL отдельно от опубликованной
  страницы и версий. Его наличие не делает несуществующую страницу опубликованной.
- Редактор видит подтверждённое состояние сохранения черновика. Сетевой сбой не
  отображается как успешное сохранение. Уход с несохранённым текстом требует явного
  решения; обещание сохранности не распространяется на текст, не дошедший до сервера.
- Сохранение, переименование, удаление и восстановление включают ожидаемую текущую
  ревизию. Проверка доступа и изменение атомарны; отзыв роли не обходится старым
  открытым редактором. Конфликт не превращается в last-write-wins.
- Повтор одного запроса после потери ответа не создаёт лишнюю версию.
- Читатель видит историю доступной действующей страницы; корзина и её история
  доступны редакторам и владельцу. Собственные черновики не открываются соавторам.

### Приватные привязки подписок

Для привязки одновременно нужны владение подпиской и доступ на чтение выбранной
страницы. Привязка принадлежит владельцу подписки, а не участникам неймспейса.
Wiki API не возвращает обратный список подписок, их названия, статьи или счётчики.

Переименование страницы не ломает привязку по ID. При удалении страницы или потере
доступа связь не уничтожается: в подписке отображается недоступность без новых
данных о странице, остаётся возможность отвязать или выбрать другую страницу.
После восстановления доступа/страницы та же привязка снова разрешается.

## Архитектура

Следовать существующему Rust/PostgreSQL/Preact стеку, не внедрять отдельный MediaWiki.
Вики независима от reader-workspace: доступ к неймспейсу и доступ к подпискам —
разные контракты и не наследуются друг от друга.

- `reader-wiki`: типы, проверенные команды, политика ролей, разбор wiki-ссылок,
  операции с версиями и порты репозитория. Без зависимостей от HTTP и PostgreSQL.
- `reader-storage-postgres/wiki/`: транзакции, поиск, версии, черновики, права,
  согласованность ссылок. Не раздувать общий repository.rs.
- `reader-server/wiki/`: аутентификация, CSRF, DTO и маршруты; не повторять правила
  доступа в отдельных обработчиках. Публичные контракты — в server-contracts.
- `web/src/wiki/`: страницы, редактор, история, корзина, доступ и локальное состояние
  раздела. ReaderApplication только подключает раздел; API — в `web/src/api/wiki.ts`.
- Связь с подпиской — отдельная небольшая операция с проверкой двух областей прав,
  не перенос ReaderRepository внутрь вики и не взаимная зависимость модулей.

Предлагаемая модель PostgreSQL:

| Таблица | Назначение |
|---|---|
| wiki_namespaces | ID, владелец, название, ревизия |
| wiki_members | namespace_id, account_id, роль |
| wiki_pages | namespace_id, ID, актуальная ревизия, состояние корзины |
| wiki_page_names | namespace_id, точное имя, page_id, признак текущего имени |
| wiki_revisions | namespace_id, page_id, версия, имя, полный Markdown, автор, время, тип изменения |
| wiki_drafts | namespace_id, page/draft ID, автор, базовая ревизия, текст |
| wiki_links | namespace_id, исходная страница, точное целевое имя; перестраиваемая проекция |
| subscription_wiki_links | владелец, subscription_id, namespace_id, page_id |

Связи страниц, алиасов, истории и внутренних ссылок включают namespace_id.
Составные внешние ключи запрещают подставить страницу другого неймспейса.
Переход к версии, корзине, поиску или алиасу требует той же проверки доступа,
что и чтение страницы. Все запросы параметризованы и ограничены областью доступа.
Отдельные таблицы/БД на неймспейс не нужны: изоляция логическая, с независимыми ACL.

## Безопасность и эксплуатация

- Нужна действующая сессия; закрытый неймспейс — состояние по умолчанию.
- Чужие ID, названия, сниппеты, число результатов, алиасы, история и подсказки не
  должны появляться в ответах без доступа. Для недоступных объектов — единый 404.
- После отзыва доступа новые чтения и изменения запрещены. Переключение аккаунта
  очищает клиентское состояние вики; запоздалые ответы другого аккаунта/неймспейса
  не отображаются. Ответы с приватным содержимым не кэшируются публично.
- Уже прочитанный/скопированный человеком текст технически нельзя отозвать.
- Отзыв доступа и сохранение сериализуются на уровне транзакции: изменение не может
  подтвердиться с правами, отозванными до его проверки/записи.
- Безопасный рендеринг, защита от XSS и CSRF, запрет исполнения кода и серверного
  получения произвольных ресурсов из Markdown. Вики не отправляется в DeepSeek.
- Логи содержат действия, ID и длительность, но не Markdown, черновики или поисковые
  строки. Все обращения к БД используют общую инструментированную границу.
- Размер страницы, пределы имён, размер поисковой выдачи и интервалы сохранения
  черновика — явные проверяемые настройки, одинаковые на клиенте и сервере.
- История сохраняет полные версии в PostgreSQL; рост объёма наблюдаем, автоматического
  удаления старых версий нет. Резервное копирование включает все новые таблицы.
- Обновление схемы — отдельная проверяемая операция с резервной копией до выкладки.

## Не входит в первую версию

Автогенерация страниц из статей; импорт вики; вложения; WYSIWYG; совместное
редактирование в реальном времени; публичные страницы; права на отдельные страницы;
группы пользователей; передача владения; удаление неймспейсов; окончательное удаление
страниц; межнеймспейсные ссылки/поиск; AI-функции вики; воспроизведение всего MediaWiki.

## Критерии приёмки

1. Два владельца создают одноимённые страницы в разных неймспейсах: данные, ссылки,
   история, черновики и поиск не пересекаются.
2. Гость и залогиненный посторонний не читают страницу, историю, алиас, поиск или
   корзину по прямому URL/API. Изменение UUID или namespace_id не обходит защиту.
3. Роли проверяются на сервере: читатель не пишет, редактор не меняет ACL, владелец
   управляет доступом. Администратор приложения не получает неявный доступ к вики.
4. Отзыв доступа действует и для открытого редактора, и для ранее полученной ссылки;
   гонка отзыва и сохранения не допускает неавторизованной записи.
5. `[[Новая страница]]` не создаёт пустых записей; после явного сохранения ссылка
   работает. Для читателя она не становится способом создания страницы.
6. Переименование сохраняет ссылку через алиас. Конфликт имён отклоняется без
   перезаписи данных. Межнеймспейсные ссылки не создаются альтернативным синтаксисом.
7. Одновременные изменения дают конфликт; оба текста доступны автору конфликта,
   опубликованная версия не теряется. Повтор запроса не создаёт дубли истории.
8. Удаление и восстановление сохраняют ID, версии и приватные привязки. Читатель
   не открывает удалённый текст через старую ревизию.
9. Участник вики не получает подписки и статьи через привязку. Удаление подписки
   не уничтожает страницу; потеря доступа не уничтожает саму приватную связь.
10. Поиск исключает чужие неймспейсы, черновики, историю и корзину; выдача ограничена
    страницей результатов. Нет загрузки всей вики в браузер ради поиска.
11. Markdown/XSS-фикстуры, опасные URL и прямые API-вызовы не обходят ограничения.
12. Нажатия и сетевые операции имеют мгновенную обратную связь, повторный клик не
    дублирует изменение, соседние кнопки не сдвигаются. Проверить в браузерных тестах.
13. Реальные PostgreSQL-тесты покрывают транзакции, составные ключи, гонки, миграцию
    и backup/restore; полный check-release проходит перед выкладкой.

## Риски и оставшиеся вопросы

Основные риски: неполная авторизация вторичных API, смешение кешей разных областей,
конфликты имён и редактирования, рост истории и потеря несохранённого черновика.
Для каждого выше указан контракт и необходимая проверка.

Существенных вопросов для продолжения интервью не осталось. Согласованные
контракты реализованы; эксплуатационные лимиты заданы явно в конфигурации.
Архитектура, индексы и проверенные границы описаны в [архитектуре Wiki](wiki-architecture.md).
