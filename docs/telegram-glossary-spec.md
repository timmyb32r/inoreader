# Определения сущностей по статье и архиву @reading_data_news

Статус: **утверждена пользователем 2026-09-27 командой «реализуй»; реализация начата**.
Решения пользователя записаны в [интервью](telegram-glossary-interview.md).
Ниже отдельно сформулированы предлагаемые точные правила, которые утверждаются
вместе со спецификацией. Описание не является отчётом о работающей поставке.

## 1. Цель и объём

По кнопке у открытой статьи получить список компаний, продуктов, технологий,
аббревиатур и протоколов с объяснениями. Сначала показать новые определения —
готовые для публикации абзацы в авторском стиле @reading_data_news. После
разделителя показать определения, уже опубликованные в канале, со ссылками.

Начальная история — существующие 1 529 постов. Новые публикации поступают через
отдельного бота, созданного владельцем через BotFather. Отдельный номер телефона
и пользовательская MTProto-сессия в решении не используются.

В объём не входят публикация или редактирование сообщений в Telegram, обучение
весов модели, новый цикл анкет на 20 текстов, конструктор стилей, семантическое
объединение названий и внешний поиск для проверки сгенерированных определений.
Сохранение или копирование AI-ответа не делает термин «известным в канале».

## 2. Сценарий пользователя

1. Рядом с `Summarize` и `文` расположена кнопка **«Термины»** с иконкой книги.
   Она работает для полного текста статьи и настроенного ключа DeepSeek.
   Если условие не выполнено, причина доступна в подсказке и через клавиатуру.
2. Нажатие сразу открывает фиксированное плавающее окно и показывает pending
   на кнопке. Повторное нажатие открывает то же задание, не вызывает модель ещё раз.
3. В окне: название статьи, закрытие, прокручиваемое содержимое. Наверху —
   **«Новые определения · N»**, ниже разделитель и **«Уже в канале · M»**.
   Пустой блок содержит короткую подпись; третий основной раздел не появляется.
4. Каждое новое определение начинается с **точного названия** и ` — `.
   Это самостоятельный русский абзац; допустим короткий список, если без него
   объяснение хуже. Кнопка копирования — значок, а не длинная текстовая кнопка.
   Есть один значок «Скопировать новые определения» для всего верхнего блока.
5. Известное определение показывается дословно из последней подходящей публикации,
   с исходным форматированием и ссылкой на неё. Оно не переписывается DeepSeek.
   Более ранние определения не раскрываются отдельным списком.
6. После повторного открытия готовый результат берётся из БД. Новая генерация
   запускается только отдельным явным действием. Закрытие окна не отменяет уже
   оплачиваемый запрос и возвращает к той же статье, без цепочки модальных окон.

Панель использует существующие semantic tokens, общие элементы копирования,
рендер Markdown и механику плавающих окон. На узком экране занимает фиксированную
область поверх статьи. Заголовок, область статуса и кнопки имеют заранее заданные
размеры. Окно не переставляет статью, toolbar и соседние hit targets.
Новое окно появляется вне координат повторного нажатия инициирующей кнопки.
Поля настройки подключения используют общий `AutofillResistantField`; bot token
не является учётными данными для входа в Reader и не использует `AuthField`.

Одна постоянная компактная строка показывает состояние источника, например:
«Канал: синхронизирован 14:35 · история может быть неполной». Подробности покрытия
и ошибки находятся в настройках источника. Для новых пояснений есть краткая
пометка «DeepSeek · без внешней проверки» вне копируемого текста.

Если после синхронизации термин становится известным, перегруппировка результатов
происходит при следующем открытии. Уже читаемый список остаётся стабильным;
обновление доступно явно через зарезервированную строку статуса.

## 3. Точные правила определений и совпадений

Предлагаемый именованный контракт: `channel_definitions_v1`.
Это явная индексная проекция; исходные посты и их поля не изменяются.

### Что считается опубликованным определением

- Пост разбирается по структуре форматирования, а не регулярным выражением
  поверх HTML. Для архива сохраняются исходный HTML и происхождение; для Bot API —
  исходный JSON, текст/caption и entities. Поддержанные rich-text блоки приводятся
  к той же структуре с сохранением исходного представления.
- Начало абзаца — начало сообщения, отдельного блочного абзаца либо после пустой
  строки. Два последовательных `<br>` соответствуют пустой строке; одиночный
  перенос остаётся частью абзаца. Абзацы списков сохраняют свои границы.
- Абзац начинается непосредственно с непустого термина, целиком покрытого bold.
  За термином следуют пробел, один из `-`, `–`, `—`, пробел и непустое объяснение.
  Для грамматических пробелов допускаются U+0020 и U+00A0; их исходные позиции и
  значения сохраняются. Bold может включать разделитель; вложенные ссылки или
  italic не отменяют bold. Маркер списка перед термином не удаляется автоматически.
- Термин — точный фрагмент перед разделителем. Название с внутренним дефисом,
  например `Wi-Fi`, не разрезается. Слова перед bold, отсутствие разделителя или
  упоминание в середине абзаца не удовлетворяют правилу.
- Сохраняется весь абзац, включая однострочные переносы, списки, ссылки и выделение.
  Следующий самостоятельный абзац не присоединяется по догадке.
- Правило структурное: модель не решает, какой пост «на самом деле определяет»
  термин. Например, `<b>Microsoft Fabric</b> становится ...` без разделителя не
  является определением. Исходный пост при этом остаётся в архиве.
- Неподдержанное форматирование и некорректные offsets получают явный статус
  `unindexed`, сохраняются для повторной обработки и не выдаются за успешно
  проиндексированные. Новый формат не должен молча терять bold.

Bot API задаёт диапазоны форматирования в UTF-16 code units. Преобразование
проверяется на границах символов, включая emoji; смещение в байтах UTF-8 не
подставляется вместо него. [Контракт Telegram](https://core.telegram.org/bots/api#messageentity).

### Известность и самое свежее определение

- Сопоставление названия **точное и с учётом регистра**. Нет stemming, перевода,
  case folding, Unicode-нормализации, удаления скобок или автоматических aliases.
  `CDC`, `cdc` и `Change Data Capture` — разные ключи.
- «Уже в канале» означает наличие подходящего определения с этим написанием
  в наблюдавшихся данных. Это не доказательство тождества смыслов у омонимов.
  Контекст поста доступен по ссылке; произвольное смысловое объединение запрещено.
- «Новые» означает «не найдено в нашем индексе», а не доказанное отсутствие во
  всей истории канала. Неполное покрытие явно отражено в состоянии источника.
- Для одинакового названия выбирается пост с наибольшим `message_id` в данном
  канале: порядок публикаций не зависит от отсутствующей даты у части архива.
  Редактирование старого поста обновляет его текст, но не делает его новее поста,
  опубликованного позднее. Если в одном посте несколько таких абзацев, побеждает
  последний по позиции; остальные сохраняются в исходной проекции.
- Применяются все доступные посты канала, включая пересланные, если они подходят
  под объявленное структурное правило. Принадлежность цитируемого текста автору
  канала не выдумывается; метаданные пересылки сохраняются.

## 4. Поставка Telegram

### Начальная загрузка

Импорт читает существующий `corpus/posts.jsonl`, inventory и сохранённые raw pages.
Все 1 529 записей сохраняются, в том числе посты без текста и даты. Повторный импорт
того же артефакта идемпотентен. Неизвестные поля не выбрасываются из raw-данных.
Конфликт идентичности или содержимого одной записи сохраняется как конфликт,
а не разрешается молчаливым last-write-wins.

В текущем архиве 13 ненаблюдавшихся ID и шесть записей без видимой даты.
Это не доказательство удаления и не основание придумывать дату.
Существующий исследовательский корпус не перезаписывается.
См. [исходный отчёт покрытия](research/channel-inventory.md).

### Новые посты

Предлагается Bot API `getUpdates` с long polling: достаточно одного приложения
на существующем сервере, публичный webhook не требуется. Один активный reader
на отдельного бота обеспечивается lease и fencing; тот же бот не используется
другим потребителем. Настроенный чужой webhook вызывает понятную ошибку,
не удаляется автоматически и не сбрасывает pending updates.

Настройка проверяет bot identity, числовой ID и username нужного канала,
членство/доступ, отсутствие конкурирующего получателя и сетевую доступность.
Бот получает публикации каналов, в которых состоит.
[Документация о получаемых сообщениях](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get).

Порядок обработки:

1. Получить batch обновлений через общий HTTP-клиент.
2. Сохранить исходные обновления и следующий offset одной транзакцией PostgreSQL.
3. Только после commit послать следующий `getUpdates` с этим offset.
4. Отдельно построить текущие посты и индекс; ошибки проекции сохраняются для replay
   и ухудшают видимый статус индекса. Подтверждение Telegram означает сохранённый
   raw event, а не обещание завершённой проекции.

Повтор того же update не создаёт второй пост. Конфликт payload для одного update
не игнорируется. Старый lease не может ни записать cursor, ни подтвердить новый
batch после потери владения. Пробелы в update/message IDs сами по себе не считаются
потерей: номера не обязаны образовывать непрерывную последовательность.
Сохранённые события вне настроенного канала не входят в его индекс.

### Редактирования и восстановление пропусков

Новые `channel_post` обновляют текущий пост, `edited_channel_post` — известную
боту запись. Неупорядоченное старое событие не откатывает более новую редакцию;
неразрешимый конфликт сохраняется отдельно. Переиндексация поста атомарно заменяет
его определения и увеличивает ревизию индекса. Удаление bold/определения при
подтверждённом редактировании исключает его из текущего индекса, не удаляя raw.

У Telegram pending updates хранятся не дольше 24 часов. Bot API не даёт общего
архивного чтения канала; события правок относятся к известным боту постам.
[Ограничения доставки](https://core.telegram.org/bots/api#getting-updates).

Поэтому в проект включается **сверка публичной истории**:

- При подключении пройти публичную ленту от настоящего времени до перекрытия
  с импортированным архивом, параллельно уже сохранять события бота.
- После длительного разрыва повторить проход по пропущенному интервалу.
- Периодически обходить доступную историю для обнаружения правок старых постов;
  предлагаемый конфиг `history_reconcile_interval = 24h`.
- HTML-наблюдение с более поздним временем получения не считается само по себе
  более новой редакцией, чем Bot API: страницы могут быть закэшированы. Явные
  edit metadata учитываются; конфликт без основания для порядка сохраняется,
  затронутый результат помечается устаревшим до разрешения.
- Отсутствие поста в выдаче не считается удалением. Гарантированная автоматическая
  синхронизация всех удалений не обещается; сохранённые определения сохраняют
  происхождение и статус последней проверки.

Публичный сбор использует `t.me/s` через общий HTTP-клиент, с ограничениями темпа
и полным сохранением возвращённого HTML. Доступ через стороннее зеркало не
включается скрыто: старый архив частично получен через Jina, но это не настройка
новой поставки. Любой proxy/зеркало требует явной конфигурации и маркировки
происхождения. Предоставленный ранее MTProto proxy не является HTTP-прокси Bot API.

Если публичная выдача недоступна, бот продолжает сохранять новые события, а
непроверенный исторический интервал остаётся видимым. Нельзя объявить поставку
полной только потому, что бот сейчас доступен. До первого успешного импорта
генерация не подменяет отсутствующий индекс пустым «все термины новые».

### Эксплуатационные параметры

Все лимиты задаются конфигурацией и валидируются до запуска: polling timeout,
HTTP deadline, lease, batch size, page/response bytes, backoff, темп публичного
обхода и интервал сверки. Предлагаемые значения: long poll 30s, deadline 45s,
lease 120s с продлением и fencing, batch до 100; согласованность лимитов проверяет
конструктор. При 429 учитывается `retry_after`. Превышение лимита не означает
обрезку текста или пропуск страницы; обход останавливается с сохранённым cursor.

## 5. DeepSeek и авторский стиль

По одному явному запуску выполняется **один запрос Flash без thinking** через
существующий provider. Вход: закреплённый полный текст и заголовок статьи,
версия промпта определений и фиксированные примеры авторской формы.
Весь архив канала не отправляется в каждый запрос.

Модель возвращает структурированный список: точное написание сущности из статьи,
тип, полный самостоятельный абзац объяснения
и признак нехватки контекста, если раскрытие неоднозначно. Кандидаты должны
принадлежать одной из пяти заявленных категорий; меню, URL, авторы-люди и
рекомендации других статей сами по себе не становятся терминами.

Сервер проверяет JSON, завершённость ответа, обязательные поля, типы, наличие
точного name как непрерывного фрагмента снимка и согласованность записей.
Само имя служит точным фрагментом; отдельная модельная цитата не требуется:
производственная проверка выявила изменение пробелов в таких цитатах при верных именах. Неподдержанные поля не
исчезают: raw-ответ сохраняется, нарушение контракта видно как ошибка. Названия
не переводятся и не заменяются моделью. Повторные упоминания одного точного имени
объединяются в одну карточку с сохранением всех упоминаний; разные имена не
склеиваются. Противоречащие друг другу определения одного имени в одном ответе
не разрешаются молчаливым выбором первого.

После валидации один пакетный запрос в индекс определений делит список на новые
и известные. Определения для известных берутся из канала; соответствующий AI-текст
не показывается как авторская цитата. Один вызов может написать ненужные пояснения
для известных слов — это небольшой расход вывода, позволяющий избежать второго
последовательного запроса и передачи всего словаря модели.

Промпт — отдельный `prompts/reading-data-news/definitions/`, а не полный prompt
пересказа с заголовком, источником и TL;DR. Он переносит уже согласованные правила
языка из [авторского профиля](../prompts/reading-data-news/style.md):

- **Термин — что это, для чего нужно, какая существенная особенность.** Для
  сокращения — полное название, если оно известно; расшифровку по буквам не угадывать.
- Для компании — чем она занимается; для продукта — назначение; для технологии
  или протокола — механизм и полезное отличие. Без рекламных оценок и каталога фич.
- Разговорный инженерный русский, привычные технические слова, короткие предложения.
  Не имитировать личный опыт, эмоции или мнения автора. Не вставлять вступление,
  TL;DR, заключение и предложение продолжить.
- Обычное определение — ориентировочно 1–4 предложения; механизм можно раскрыть
  подробнее. Это ориентир письма, а не обрезка по длине.
- Использовать статью и знания DeepSeek без web search. Не придумывать неизвестную
  расшифровку или спорные подробности. Недостаток контекста обозначать прямо.
- Название выделять жирным, абзац делать самостоятельным и пригодным для копирования.
  Метки интерфейса и сведения о синхронизации не включать в копируемый текст.

До реализации промпта выбрать несколько настоящих определений из архива и
зафиксировать происхождение примеров. Исходный summary prompt и результаты его
оценки не переписывать. Предыдущие 20/20 по пересказам не объявлять оценкой качества
нового глоссария. Новый исследовательский бюджет не считать разрешённым автоматически;
на этапе проектирования платных запросов нет.

Ошибка, неполный ответ и превышение контекста не превращаются в пустой успешный
список. Статья не обрезается. Неопределённо завершившийся оплачиваемый запрос не
повторяется автоматически; явный retry создаёт новую попытку с сохранением прежней.

## 6. Данные, границы модулей и API

Новый небольшой Rust crate `reader-glossary` владеет моделью канала/определений,
валидированными контрактами, парсером, синхронизацией Telegram и портом хранения.
Модули внутри разделены по ответственности: `model`, `definition_parser`,
`telegram`, `sync`, `repository`. Не создаётся универсальная ETL-платформа.

Raw DTO, редактируемый config и валидированные `ChannelBinding`, `ObservedPost`,
`DefinitionSpan`, `DefinitionResult` — разные типы. Конструкторы проверяют
идентичность, диапазоны текста, форматирование и непротиворечивость; поля инвариантов
закрыты. Десериализация и изменение проходят ту же границу. Сетевое обнаружение
проверяется после получения metadata, до старта worker. Неизвестные исходные поля
сохраняются в raw; строгая проверка исполняемого контракта не оправдывает их потерю.

- `reader-ai`: отдельный модуль `definitions` с промптом, provider-вызовом,
  результатами и job lifecycle; использует glossary domain, не наоборот.
- `reader-storage-postgres`: модули хранения raw events, текущих постов,
  индексных проекций и AI jobs. Новые таблицы входят в существующий backup/restore.
- `reader-server`: тонкие маршруты glossary/settings, auth и CSRF; логика разбора
  не добавляется в большой файл роутов.
- `web/src/glossary`: панель, hook задания, результаты и собственные тесты.
  Общие примитивы остаются общими; AI-чат не дублируется целиком.
- `inoreader`: только composition/config/startup. Производственных Python-скриптов
  или новых sidecar-сервисов нет.

Основные сущности хранения:

| Объект | Идентичность и содержимое |
|---|---|
| Channel connection | owner, workspace, numeric channel ID, username, encrypted bot credential, config, state |
| Raw receipt / import | точный payload, provenance, update/import identity, время наблюдения, исходные поля |
| Current post | одна логическая запись на connection + channel ID + message ID; текст/formatting и указатель на подтверждённую редакцию |
| Definition projection | post + paragraph position + parser version; точное имя, исходный абзац и ссылка |
| Index revision / coverage | revision, наблюдавшиеся интервалы, gaps, неприменённые события и ошибки |
| Article definitions job | owner/workspace/article + snapshot + model/prompt/config, operation ID, ответ, статус, usage/cost |

Raw observations служат явным журналом происхождения; они не становятся несколькими
текущими постами с одним primary key. Индекс строится заново из сохранённых данных
без повторного платного обращения. Индексы PostgreSQL начинаются с owner/connection;
поиск имён — пакетный и с точной семантикой сравнения. Нет запроса всей истории
канала или всех статей при открытии reader.

Предлагаемый API:

- `GET/PUT /api/glossary/channel`: настройки и статус источника в принадлежащем
  пользователю workspace; GET не возвращает bot token.
- `POST /api/glossary/channel/sync`: идемпотентное задание сверки публичной истории.
- `POST /api/articles/{id}/definitions`: workspace + operation ID; server сам
  загружает разрешённый снимок статьи, клиент не подменяет полный текст.
- `GET /api/articles/{id}/definitions`: сохранённый результат/состояние задачи;
  опрос только пока задание выполняется, без постоянного фонового polling UI.

Ключи, кэш, задания, канал и определения принадлежат аккаунту/workspace.
Сходство публичных статей не разрешает доступ к чужим результатам. Конфигурация
канала v1 доступна владельцу авторского профиля; другие аккаунты не подключаются
к его боту или стилю автоматически. Удаление API-ключа запрещает новые платные
вызовы, сохраняя уже полученные данные.

Дедупликация paid jobs выполняется транзакционно по точному входу и версии промпта;
один operation ID с другим входом — конфликт. Обновление индекса канала позволяет
переклассифицировать сохранённые сущности без повторного вызова DeepSeek. Хэш может
ускорять поиск, но не заменяет сравнение исходных значений и не служит единственным
доказательством равенства.

Все HTTP-вызовы идут через общий outbound boundary с DNS/IP/redirect policy,
лимитами и общим timing. Bot token находится в URL path Bot API: его нужно
редактировать в диагностике **до** форматирования ошибки; URL целиком, payload,
ответы и ключи в технические логи не попадают. На другом origin запрос с token
не повторяется. Шифрование использует существующий проверенный механизм хранения
секретов, без копии криптографической реализации в Telegram-модуле.

Метрики: длительности Telegram/DeepSeek/SQL, cursor commit, lag применения событий,
последняя успешная сверка, pending/unindexed/conflicts, количества постов и
определений, токены и расходы. Отсутствие новых публикаций само по себе не ошибка:
здоровье оценивается по успешным poll и состоянию обработки, а не возрасту поста.

## 7. Приёмка и проверки

1. **Импорт:** все 1 529 исходных записей сохранены с raw и provenance; 13 gaps
   и шесть отсутствующих дат отражены; повтор импорта ничего не теряет и не дублирует.
2. **Парсер:** три разделителя, bold/strong, вложенная разметка, Unicode/emoji,
   NBSP, многострочные определения и списки; упоминание в середине и bold без
   разделителя не принимаются. Сохраняются точные имена и текст исходного абзаца.
3. **Выбор:** одинаковое имя в нескольких постах даёт последнее опубликованное
   определение; правка старого не меняет порядок публикаций; разные написания
   не объединяются. Пересылки и nullable dates обрабатываются явно.
4. **Поставка:** реальные транзакции PostgreSQL, повтор batch, перезапуск до/после
   commit, expired lease, два worker, edited post, 429, недоступный Telegram,
   malformed/unsupported event и конфликт payload. Cursor никогда не подтверждает
   несохранённые данные. После исправления парсера raw event воспроизводится.
5. **Покрытие:** промежуток архив → активация бота сверяется; недоступная публичная
   история и outage >24h остаются видимыми непроверенными интервалами. Отсутствующий
   пост не удаляется по предположению.
6. **AI:** на зафиксированных разнородных статьях проверяются все пять категорий,
   точные упоминания, повторения, русский/английский/китайский текст, пустой список,
   malformed/truncated response, неоднозначное сокращение и prompt injection.
   Модельная полнота оценивается отдельно; валидация JSON не доказывает, что найдены
   все сущности. Декларация гарантированной безошибочности не допускается.
7. **Копирование:** одиночное определение и все новые копируются в правильном
   порядке с bold в rich clipboard и Markdown/plain-text альтернативой. Известные
   не попадают в «копировать новые»; служебные метки не попадают в пост.
8. **UI:** Chromium проверяет pointer/keyboard, немедленный pending, отсутствие
   повторного paid job, стабильность toolbar/окна/кнопок, закрытие к той же статье,
   mobile/dark theme и отсутствие перегруппировки под активным курсором.
9. **Изоляция и секреты:** нельзя получить чужой job/пост/конфиг; нет token в API GET,
   логах и ошибках, включая URL path/redirect failures. HTTP regression покрывает
   запрещённые адреса, все redirect hops, loops/limits и секреты между origins.
10. **Хранение:** backup/restore новых таблиц с реальным PostgreSQL; нет потери raw,
    cursor, известных определений или готовых результатов. Тесты отдельно от кода.
11. **Релиз:** `just check-affected` для затронутых пакетов, затем полный
    `just check-release` с обязательными контейнерными проверками. После деплоя —
    реальное получение свежего поста/редакции и проверка определения в UI.

Синтетические транспортные тесты не заменяют проверку работающего бота. Если свежего
поста ещё не было, так и записывается; агент не публикует тестовое сообщение в
публичный канал без отдельного явного поручения.

## 8. Порядок реализации, риски и открытые зависимости

После утверждения: (1) доменные контракты и парсер с импортом; (2) надёжная поставка
и статус покрытия; (3) Flash prompt/job/API; (4) панель и копирование; (5) интеграционные
проверки, backup, деплой и проверка на реальных данных. Сначала данные и их
происхождение, затем классификация и UI. Уже работающие summary/translation
сохраняют свои контракты и не перестраиваются ради общей абстракции.

Материальные ограничения: публичный архив не доказывает полную историю; бот не
восстанавливает произвольную историю самостоятельно; автоматическое определение
всех удалений недоступно; точное сопоставление пропустит варианты написания;
знания DeepSeek могут быть ошибочны или устареть. Эти ограничения видны в контрактах,
метках происхождения и статусе поставки, а не маскируются успешным пустым ответом.

Открытые зависимости запуска: владелец создаёт отдельного бота и добавляет его в
канал, секрет вводится защищённо; проверяется доступ сервера к Bot API и публичной
истории. Исторические таймауты прямого Telegram-доступа требуют свежей проверки,
а не предположения, что MTProto proxy решает HTTP-доступ. Если нужна отдельная
сетевая конфигурация, она обсуждается по конкретному результату проверки.

Пользователь утвердил спецификацию, включая правила раздела 3, командой «реализуй».
На этапе интервью production-код не менялся, платных запросов и деплоя не было.
При старте реализации пользователь сообщил, что бот ещё не создан. Код поставки,
импорт и UI реализуются независимо; живой приём требует последующего подключения
бота владельцем. Ход работы: [журнал реализации](tasks/telegram-glossary-2026-09-27.md).
